# Диагностика и восстановление «Складского учёта» (runbook)

Инструкция для дежурного: что делать, когда сработало оповещение или
пользователь сообщил о проблеме. Каждое правило оповещения
(`monitoring/prometheus/rules/warehouse.yml`) ссылается на раздел этого
файла; `make monitoring-lint` проверяет, что разделы существуют.

Команды `make` выполняются в каталоге репозитория (локальное окружение). На
серверах те же сценарии лежат в файлах выпуска и запускаются от имени
`deploy` с указанием проекта и адреса:

```bash
cd /opt/warehouse-stage/current        # production: /opt/warehouse-prod/current
sudo -u deploy PROJECT=warehouse-stage URL=http://192.168.56.20:8080 ./scripts/obs.sh status
sudo -u deploy PROJECT=warehouse-stage ./scripts/logs.sh -l ERROR -t 30m
```

`make status` ↔ `scripts/obs.sh status`, `make logs-find ...` ↔
`scripts/logs.sh ...` (параметры — `scripts/logs.sh --help`).
Контейнеры называются `<проект>-<сервис>-1`: `warehouse-stage-app1-1`.

## Порядок диагностики

1. **Масштаб.** `make status` — контейнеры, доступность через Nginx, цели
   сбора метрик, оповещения, ключевые метрики и ошибки в журналах на одном
   экране. Панель Grafana «Складской учёт — обзор» (`make grafana`).
2. **Компонент.** Путь запроса: клиент → Nginx :8080 → app1/app2 :8000 →
   PostgreSQL; под ними — контейнеры и хост. Ищите первое звено, которое
   «красное»: таблица ниже.
3. **Причина — двумя источниками.** Метрика показывает *что* и *когда*,
   журнал — *почему*. Гипотеза подтверждена, если они согласуются
   (например, `warehouse_database_up = 0` и в журнале `db_unavailable`
   с текстом ошибки подключения).
4. **Восстановление** — по разделу ниже. Сначала вернуть работу
   пользователям (откат, перезапуск), потом устранять причину.
5. **Проверка.** `make smoke` (для сервера — `URL=http://<адрес>:8080`),
   `make status`: оповещение перешло в `resolved`, метрики в норме.
6. **Запись.** Разбор инцидента — `docs/incidents/` по шаблону
   [`TEMPLATE.md`](incidents/TEMPLATE.md), с улучшением процесса.

### Признак → компонент

| Что видно | Где проблема | Раздел |
|---|---|---|
| `/healthz` через Nginx не отвечает, соединение отклонено | Nginx, порт, firewall | [1](#1-сервис-недоступен), [8](#8-порт-недоступен) |
| Nginx отвечает 502/504 на всё | оба экземпляра приложения | [4](#4-экземпляр-перезапускается-или-остановлен) |
| `/healthz` 200, `/readyz` 503, ошибки 500 на API | база данных или её настройки | [2](#2-база-данных-недоступна), [11](#11-неверная-конфигурация) |
| Работает, но один экземпляр unhealthy | этот экземпляр | [4](#4-экземпляр-перезапускается-или-остановлен) |
| Рост 5xx сразу после выпуска | новая версия | [6](#6-ошибка-новой-версии) |
| Медленные ответы, память у лимита, перезапуски с `OOMKilled` | ресурсы контейнера | [5](#5-нехватка-памяти-или-ресурсов) |
| База не принимает записи, копии не создаются | диск хоста | [3](#3-нехватка-места-на-диске) |
| Много 401, изменения отклоняются | учётные данные, права | [7](#7-нарушение-прав-доступа) |
| Секрет в журнале | код или конфигурация журналирования | [9](#9-утечка-секрета-в-журнал) |

### Инструменты

| Команда | Что показывает |
|---|---|
| `make status` | сводка по всем источникам |
| `make alerts` | сработавшие оповещения и раздел инструкции |
| `make logs-find LEVEL=ERROR SINCE=30m` | ошибки в журналах приложения и Nginx |
| `make logs-find ID=<request_id>` | путь одного запроса: Nginx → экземпляр (request_id — заголовок `X-Request-ID` ответа) |
| `make logs-find EVENT=http_request CODE=5` | ответы 5xx с адресом операции и экземпляром |
| `make metrics-query Q='<PromQL>'` | любое значение метрики (Prometheus наружу не открыт) |
| `make ps`, `docker inspect <контейнер>` | состояние, healthcheck, `RestartCount`, `OOMKilled`, `ExitCode` |
| `docker logs --tail 50 <контейнер>` | журнал контейнера целиком (в т. ч. не JSON: PostgreSQL, Prometheus) |
| `deploy/stage/deploy.sh status` (на сервере) | что развёрнуто, история выпусков |

## 1. Сервис недоступен

**Оповещение:** `WarehouseUnavailable` — проверка `http://nginx:8080/healthz`
не проходит больше минуты (blackbox, как у пользователя).

**Диагностика**

1. `make status` — раздел «Доступность через Nginx» и «Контейнеры».
2. Nginx запущен? `docker inspect -f '{{.State.Status}} {{.State.Health.Status}}' <проект>-nginx-1`.
3. Если Nginx работает, а ответ 502/504 — проблема за ним: оба экземпляра
   (раздел 4) или база (раздел 2). `make logs-find S=nginx CODE=5` — поле
   `upstream_status` показывает ответы экземпляров.
4. Если соединение отклонено — порт (раздел 8).

**Восстановление:** запустить остановленный сервис
(`docker start <контейнер>` или `docker compose up -d`; на сервере —
`make infra-apply ENV=<окружение>`: Ansible поднимет сервисы с настройками
окружения). Затем `make smoke`.

## 2. База данных недоступна

**Оповещения:** `DatabaseUnavailable` (оба экземпляра сообщают
`warehouse_database_up = 0`), `WarehouseNotReady` (`/readyz` ≠ 200).

**Диагностика**

1. `make metrics-query Q='warehouse_database_up'` — 0 у обоих экземпляров:
   база недоступна; 0 только у одного — его настройки (раздел 11).
2. `make logs-find EVENT=db_unavailable SINCE=15m` и
   `make logs-find LEVEL=ERROR` — текст ошибки подключения.
3. Контейнер базы: `docker inspect -f '{{.State.Status}} {{.State.Health.Status}} OOM={{.State.OOMKilled}}' <проект>-db-1`,
   `docker logs --tail 50 <проект>-db-1` (переполнение диска, повреждение,
   неверный пароль, остановка).
4. Причина подтверждена, если время перехода `warehouse_database_up` в 0
   совпадает с остановкой контейнера или ошибкой в журнале базы.

**Восстановление**

- остановлена — `docker start <проект>-db-1`, дождаться `healthy`; приложение
  переподключается само (пул соединений с проверкой `pre_ping`);
- нет места — раздел 3;
- неверный пароль после изменения настроек — раздел 11;
- данные повреждены — восстановление из копии: `docs/backup.md`
  (`make restore FILE=...`; на сервере копии перед выпуском —
  `/opt/<окружение>/backups/`).

**Проверка:** `/readyz` → 200 `{"database":"ok"}`, оповещения resolved,
`make smoke`.

## 3. Нехватка места на диске

**Оповещение:** `DiskSpaceLow` — свободно меньше 10% на файловой системе хоста.

**Диагностика:** `df -h`; что растёт — `sudo du -xsh /var/* /opt/* 2>/dev/null | sort -h | tail`;
Docker — `docker system df`. Частые причины: копии базы
(`/opt/<окружение>/backups`), старые образы выпусков, журналы контейнеров
(ограничены: 3 × 10 МБ на контейнер), данные Prometheus (хранятся 15 дней, не больше 1 ГБ).

**Восстановление:** удалить лишнее, а не данные базы:
`docker image prune -a --filter "until=168h"` (образы, не используемые
контейнерами), старые копии сверх пяти последних, временные файлы. Если
PostgreSQL успел остановиться — `docker start <проект>-db-1` и проверить
журнал на ошибки записи.

**Проверка:** свободно больше 10%, `make status` без оповещений.

## 4. Экземпляр перезапускается или остановлен

**Оповещения:** `ContainerRestarted` (новое время старта контейнера за 10
минут), `WarehouseInstanceDown` (Prometheus не может собрать метрики
экземпляра), `WarehouseNotReady` для одного экземпляра.

Пока работает второй экземпляр, пользователи ошибок не видят: Nginx
исключает неответивший экземпляр и повторяет запрос на другом. Но запаса
уже нет.

**Диагностика**

1. `docker inspect -f 'status={{.State.Status}} health={{.State.Health.Status}} restarts={{.RestartCount}} OOMKilled={{.State.OOMKilled}} exit={{.State.ExitCode}}' <проект>-app1-1`:
   - `OOMKilled=true`, `exit=137` — превышен лимит памяти (раздел 5);
   - `exit=1` при старте — ошибка конфигурации или кода (журнал, раздел 11);
   - `paused` или `health=unhealthy` без перезапуска — процесс завис или не
     проходит healthcheck: `docker inspect -f '{{json .State.Health.Log}}' <контейнер> | jq`.
2. Журнал до перезапуска: `docker logs --tail 50 <контейнер>`; события
   `app_started` / `app_stopped` — `make logs-find EVENT=app_started SINCE=1h`.
3. Метрика `container_start_time_seconds` на панели «Перезапуски контейнеров».

**Восстановление:** `docker unpause` / `docker start <контейнер>`;
повторяющиеся перезапуски — устранить причину (разделы 5, 6, 11), при
ошибке новой версии — откат (раздел 6).

## 5. Нехватка памяти или ресурсов

**Оповещения:** `ContainerMemoryNearLimit` (больше 90% лимита 2 минуты),
`SlowResponses` (95-й процентиль времени ответа больше 1 с 5 минут).

**Диагностика**

1. Панель «Ресурсы»: память контейнеров в % лимита, CPU, хост.
2. `docker stats --no-stream` — фактическое потребление и лимиты.
3. Время ответа по адресам: панель «p95 по адресам» или
   `make metrics-query Q='topk(5, histogram_quantile(0.95, sum by (le, endpoint) (rate(warehouse_http_request_duration_seconds_bucket[5m]))))'` —
   медленный один адрес (запрос к базе) или все (ресурсы).
4. OOM: `docker inspect -f '{{.State.OOMKilled}}'`, метрика
   `container_oom_events_total`, `sudo dmesg | grep -i oom` на хосте.

**Восстановление:** перезапустить экземпляр, утекающий памятью
(`docker restart <контейнер>` — по одному, второй обслуживает запросы);
если нагрузка выросла законно — увеличить лимит в `docker-compose.yml`
через merge request с обоснованием (`docs/containers.md`).

## 6. Ошибка новой версии

**Оповещение:** `HighErrorRate` — доля ответов 5xx больше 5% в течение
2 минут.

**Диагностика**

1. Совпадает ли начало роста ошибок с выпуском: панель «Версия» и график
   ошибок, `deploy/stage/deploy.sh status` (история выпусков).
2. Какие операции падают: `make logs-find EVENT=http_request CODE=5` —
   адрес операции, экземпляр, request_id; по request_id —
   `make logs-find ID=<id>` (запись `unhandled_error` с исключением).
3. Сравнить с состоянием до выпуска: `reports/release-before-*.md`
   (`make release-snapshot`).

**Восстановление:** сначала откат — `deploy/stage/deploy.sh rollback`
(staging) или `make infra-apply ENV=production TAG=<предыдущий тег>`;
затем исправление через обычный процесс (задача → ветка → MR → CI) с тестом,
воспроизводящим ошибку.

## 7. Нарушение прав доступа

**Оповещение:** `AuthFailuresBurst` — больше 20 отказов в доступе за 5 минут.

**Диагностика**

1. `make logs-find EVENT=auth_failed SINCE=30m` — с какого адреса (`client`
   в журнале Nginx по тому же request_id) и как часто.
2. Один клиент и постоянно — подбор пароля или клиент со старым паролем.
3. Отказы у всех после изменения настроек — пароль API в настройках
   окружения не совпадает с тем, что знают пользователи (раздел 11).
4. Права на сервере: файл настроек окружения — `600`, владелец `deploy`;
   `deploy` состоит только в группе `docker` (`make infra-verify` проверяет
   оба условия).

**Восстановление:** заблокировать источник (firewall, правило nftables
через Ansible), сменить пароль (`make vault-edit` → `make infra-apply`);
права файлов и групп — `make infra-apply` (Ansible вернёт эталонные).

## 8. Порт недоступен

Признак: соединение с `http://<адрес>:8080` отклонено или зависает, при
этом контейнеры работают.

**Диагностика**

1. Слушает ли порт: `ss -ltnp | grep 8080` на хосте.
2. Nginx опубликовал порт на нужном адресе: `docker port <проект>-nginx-1`
   (адрес `HTTP_BIND` из настроек окружения).
3. Firewall: `sudo nft list table inet warehouse` — порт разрешён из
   лабораторной сети.
4. Порт занят другим процессом — Nginx не стартует, в
   `docker logs <проект>-nginx-1` — `address already in use`.

**Восстановление:** `make infra-apply ENV=<окружение>` возвращает правила
firewall и настройки; занятый порт — остановить постороннее приложение.

## 9. Утечка секрета в журнал

**Оповещение:** `SecretRedactedInLogs` — код пытался записать в журнал
пароль или токен. Значение заменено на `***`, но это ошибка в коде:
следующая форма записи может не попасть под маскирование.

Секрет, записанный в обход журналирования приложения (`print()`, сторонняя
библиотека), маскирование не видит — его находит `make logs-secrets`
(настоящие значения паролей из `.env` и типичные формы секретов во всех
журналах; выполняется в `make container-check`).

**Диагностика:** `make logs-find TEXT='***' SINCE=1h` — какая запись и
событие; по полю `logger` — модуль; `make logs-secrets SINCE=24h`.

**Восстановление**

1. Найти и исправить запись в коде (MR с тестом в `tests/unit/test_logging.py`).
2. Если секрет попал в журнал **открыто** — считать его скомпрометированным:
   сменить (`make vault-edit` → `make infra-apply`), журналы контейнера
   пересоздаются вместе с контейнером.

## 10. Предметные оповещения

**Оповещение:** `MaterialsBelowMinimum` (severity `info`) — остаток
материалов ниже минимального дольше 15 минут. Это не сбой, а сигнал для
кладовщика: нужна закупка. Список —
`GET /api/v1/reports/stock?below_min=true`. Если число растёт резко после
выпуска — проверить, не изменилась ли логика расчёта (раздел 6).

## 11. Неверная конфигурация

Признаки: экземпляр не стартует или стартует, но `/readyz` 503; отказы в
доступе у всех после изменения настроек; выпуск не начинается
(`deploy.sh`: «не заданы переменные окружения»).

**Диагностика:** `docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' <контейнер> | grep -v PASSWORD`
— имена и несекретные значения; сравнить экземпляры между собой; журнал
старта (`EVENT=app_started`, `db_unavailable`). На сервере:
`make infra-check ENV=<окружение>` — `--diff` покажет отличие файлов от кода.

**Восстановление:** настройки сервера задаёт Ansible — `make infra-apply`
вернёт их (ручные правки отменяются). Локально — `.env` по образцу
`.env.example` и `docker compose up -d`.

## 12. После восстановления

- `make smoke` и `make status` — сервис работает, оповещений нет;
- `make release-snapshot NAME=after-incident` — состояние для разбора;
- разбор инцидента в `docs/incidents/` по шаблону: хронология, как
  обнаружили, причина (подтверждённая метриками и журналами), что
  улучшено в процессе (тест, проверка CI, метрика, оповещение, проверка
  конфигурации или шаг восстановления).
