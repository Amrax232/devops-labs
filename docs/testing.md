# Стратегия тестирования

## Уровни тестов

| Уровень | Каталог | Что проверяет | База данных | Время |
|---|---|---|---|---|
| Unit | `tests/unit` | правила предметной области в `app/domain.py` как чистые функции | не нужна | доли секунды |
| API | `tests/api` | HTTP API целиком: маршруты, валидация, ошибки, сценарии | SQLite во временном каталоге | секунды |
| Интеграционные | `tests/integration` | миграции Alembic, ограничения СУБД, работа приложения с PostgreSQL, одновременные запросы | PostgreSQL, база `warehouse_test` | десятки секунд |

```bash
make test-unit          # только unit
make test-api           # только API
make test               # unit + API: быстро, без Docker
make test-integration   # поднимает PostgreSQL и запускает интеграционные
make coverage           # все уровни + отчёты
make mutation           # мутационное тестирование правил
```

## Почему правила вынесены в `app/domain.py`

Решения «можно / нельзя» и арифметика остатков собраны в модуле без базы данных
и HTTP: на вход — значения, на выход — результат или исключение `RuleViolation`.
Слой `app/services.py` загружает данные, вызывает эти функции и сохраняет
результат. Так основная логика тестируется unit-тестами за доли секунды, а
мутационное тестирование успевает прогнать тесты для каждого мутанта.

## Изоляция тестовых данных

- **Unit-тесты** не используют базу вообще.
- **Тесты API** получают собственную SQLite-базу в каталоге, созданном
  `tempfile.mkdtemp` при запуске pytest; каталог уникален для каждого запуска и
  удаляется по завершении. Перед каждым тестом схема создаётся заново
  (фикстура `clean_database`), поэтому тесты не зависят друг от друга и порядка.
- **Интеграционные тесты** работают с отдельной базой PostgreSQL из
  `TEST_DATABASE_URL` (по умолчанию `warehouse_test`). Перед каждым тестом
  схема `public` удаляется и создаётся заново. Тесты **отказываются работать**
  с базой, имя которой не оканчивается на `_test`: случайно указать рабочую
  базу и стереть её невозможно.
- Логин и пароль API в тестах свои (`tests/conftest.py`) и перекрывают значения
  из `.env` и окружения разработчика.

## Граничные значения и ошибочные данные

Каждый параметр проверяется на границе: последнее допустимое значение
принимается, первое недопустимое отклоняется (`tests/api/test_boundaries.py`,
`tests/unit/test_domain.py`). Примеры:

| Параметр | Принимается | Отклоняется |
|---|---|---|
| ИНН | 10 и 12 цифр | 9, 11, 13 цифр, буквы |
| Количество | `0.001` | `0`, `-1`, `0.0001` (4-й знак) |
| Цена | `0`, `0.01` | `-0.01` |
| Списание | ровно весь остаток | остаток + `0.001` |
| Минимальный запас | остаток = минимуму — не дефицит | остаток на `0.001` меньше — дефицит |
| Строк в документе для проведения | 1 | 0 |
| `limit` отчёта | 1 и 500 | 0 и 501 |
| Причина списания | 3 и 255 символов | 2 и 256 символов |

Также проверяются: отсутствие обязательных полей, неверный тип, некорректный
JSON, несуществующие даты, неизвестные объекты (404), запросы без пароля (401).

## Отчёты

`make coverage` формирует в каталоге `reports/`:

| Файл | Содержимое |
|---|---|
| `junit.xml` | результаты всех тестов в формате JUnit — читается CI и IDE |
| `coverage.xml` | покрытие в формате Cobertura |
| `coverage-html/index.html` | покрытие построчно с подсветкой непокрытых строк |
| `bandit.json` | результаты SAST (`make sast`) |
| `mutation.txt` | итог мутационного тестирования и выжившие мутанты (`make mutation`) |

Порог покрытия — 80 % строк и ветвлений пакета `app` (`[tool.coverage.report]`
в `pyproject.toml`). При меньшем значении `make coverage` завершается ошибкой.

## Мутационное тестирование

`scripts/mutation_test.py` по очереди вносит в `app/domain.py` маленькие ошибки
и запускает unit-тесты для каждой:

| Мутация | Пример |
|---|---|
| сравнение | `<` → `<=`, `>` → `>=`, `==` → `!=`, `in` → `not in` |
| арифметика | `+` → `-`, `*` → `/` |
| логика | `and` → `or`, удаление `not` |
| константы | `0` → `1`, `True` → `False` |
| удаление проверки | `raise ...` → `pass`, удаление вызова функции-проверки |
| возвращаемое значение | `return x` → `return None` |

Мутант **убит**, если тесты упали, и **выжил**, если прошли — тогда в тестах
дыра. Оценка = доля убитых. Порог — 80 % (`[tool.warehouse.quality]`).
Выжившие мутанты с номером строки печатаются в консоль и в `reports/mutation.txt`.

Файлы проекта при этом не меняются: каждый мутант проверяется во временной
копии кода, байт-код не кешируется.

Ровно это и делает преподаватель на защите, меняя условие в основной логике:
например, `requested > current` → `requested >= current` в `apply_write_off`.
Тест `test_write_off_of_whole_stock_is_allowed` немедленно падает.

Почему собственный скрипт, а не mutmut: правила сосредоточены в одном модуле
без зависимостей, а скрипт на стандартной библиотеке Python делает ровно то, что
нужно, без дополнительного пакета, работает одинаково на любой машине и
проверяет порог — `make verify` падает, если тесты ослабли.
