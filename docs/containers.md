# Контейнерное окружение

Приложение и база данных запускаются в контейнерах Docker Compose. Окружение
воспроизводимо, проверяется автоматически (`make container-check`) и
поднимается одной командой `make up`.

## 1. Состав

```
клиент ──► nginx :8080 ──┬──► app1 :8000 ──┐
(edge)      (балансир)   └──► app2 :8000 ──┴──► db :5432 ── том db_data
                 app_net (internal)            db_net (internal)
```

| Сервис | Образ | Назначение | Пользователь |
|---|---|---|---|
| `db` | `postgres:16.4-alpine3.20` | PostgreSQL, данные в томе `db_data` | `postgres` (uid 70): entrypoint понижает права |
| `migrate` | `warehouse-inventory:0.7.0` | разовый: `alembic upgrade head` и завершение | `app` (uid 10001) |
| `app1`, `app2` | `warehouse-inventory:0.7.0` | два экземпляра API (uvicorn) | `app` (uid 10001) |
| `nginx` | `nginxinc/nginx-unprivileged:1.27.2-alpine` | единственная точка входа, балансировщик | `nginx` (uid 101) |

**Порядок запуска** обеспечивается `depends_on` с условиями:
`db` (healthy) → `migrate` (завершился с кодом 0) → `app1`, `app2` (healthy) →
`nginx`. Приложение не стартует на базе без миграций, nginx не принимает
запросы, пока экземпляры не готовы.

**Сети.**

- `edge` — обычная сеть, через неё опубликован порт nginx.
- `app_net` и `db_net` — внутренние (`internal: true`): выхода наружу нет,
  с хоста к ним не подключиться.
- Приложение подключено к `app_net` и `db_net`, база — только к `db_net`.
  Поэтому nginx не может обратиться к базе напрямую.

**Порты.** Наружу опубликован единственный порт — `nginx` 8080, по умолчанию
только на `127.0.0.1` (`HTTP_BIND`, `HTTP_PORT` в `.env`).

- У приложения и у базы портов на хосте нет.
- Порт PostgreSQL нужен только для разработки из `.venv` (`make run`,
  интеграционные тесты). Он открывается отдельным файлом
  `docker-compose.dev.yml` (`make dev-db`) и тоже только на `127.0.0.1`.

## 2. Образ приложения (`Dockerfile`)

| Требование | Как выполнено |
|---|---|
| Воспроизводимая сборка | базовый образ с точной версией (`python:3.12.7-slim-bookworm`); все зависимости, включая транзитивные, ставятся по `requirements.lock` (`make lock`); контекст сборки задан белым списком в `.dockerignore` |
| Небольшой образ | двухэтапная сборка: в итоговый образ копируется только готовое виртуальное окружение, без кэша pip |
| Не от root | системный пользователь `app` с фиксированным uid/gid 10001, без оболочки входа; код принадлежит root и доступен только на чтение |
| Настройки через окружение | в образе нет ни паролей, ни строки подключения: `AUTH_*`, `DATABASE_URL`, `INSTANCE_ID`, `LOG_LEVEL` передаются при запуске из `docker-compose.yml` и `.env` |
| Healthcheck | `HEALTHCHECK` обращается к `/healthz`. В compose он повторён явно, отключать его запрещено |
| Штатная остановка | `CMD` в exec-форме; в контейнере `init: true` (tini — PID 1, передаёт сигнал). По `SIGTERM` uvicorn перестаёт принимать соединения и ждёт текущие запросы до 15 с (`--timeout-graceful-shutdown`). Затем при остановке приложения закрывается пул соединений с БД, и процесс завершается сам. `stop_grace_period: 20s` больше 15 с, поэтому `SIGKILL` не нужен |

Код завершения после `docker stop`:

- **143** — процесс сам завершился по `SIGTERM` (uvicorn после штатной
  остановки повторно поднимает полученный сигнал);
- **0** — штатный выход;
- **137** — процесс не уложился в `stop_grace_period` и был убит. Это ошибка.

**Дополнительная защита контейнеров приложения и nginx:**

- `read_only: true` — корневая ФС только на чтение, временные файлы в
  `tmpfs /tmp`;
- `cap_drop: [ALL]`;
- `no-new-privileges`;
- журналы с ротацией (`max-size 10m`, 3 файла).

## 3. Данные

Данные PostgreSQL лежат в именованном томе `warehouse-inventory_db_data`.

- Том не удаляется при `docker compose down`, при пересоздании контейнеров
  (`up --force-recreate`) и при обновлении образа.
- Удалить его может только явная команда `docker compose down -v`.

Проверка сохранности — шаг 11 в `make container-check`:

1. создаётся запись;
2. выполняется `down` и `up`;
3. собирается и запускается образ с другим тегом (обновление);
4. после каждого шага проверяется, что запись на месте.

**Миграции, резервные копии, восстановление** выполняются в контейнерной среде:

| Команда | Что делает |
|---|---|
| `make container-migrate` | `alembic upgrade head` в разовом контейнере `migrate` (выполняется и автоматически при `make up`) |
| `make migrations-demo` | миграции на чистой и на заполненной базе; alembic в контейнере `migrate`, отдельная база |
| `make backup` | `pg_dump` внутри контейнера `db` (версия клиента = версии сервера), проверка архива, SHA-256 |
| `make restore FILE=...` | проверка контрольной суммы, страховочная копия, `pg_restore` одной транзакцией |
| `make restore-new-volume` | копия → **новый пустой том** в отдельном проекте compose → восстановление → сверка с рабочей базой. Рабочий том не затрагивается |

## 4. Ограничения ресурсов

Заданы для каждого сервиса (`deploy.resources.limits`). Исходные данные —
фактическое потребление, которое `make container-check` выводит через
`docker stats` на шаге 4.

| Сервис | CPU | Память | Процессов | Обоснование |
|---|---|---|---|---|
| `db` | 1.0 | 512 МБ (резерв 192 МБ) | 200 | `shared_buffers` по умолчанию 128 МБ (+ `shm_size` 128 МБ). Каждое соединение занимает несколько МБ. Пулы двух экземпляров — до 2 × 15 = 30 соединений (+ migrate), это меньше `max_connections` = 100. 512 МБ хватает с запасом, а утечка не съест память хоста. Ядро CPU — для сортировок отчётов |
| `app1`, `app2` | 0.5 | 256 МБ (резерв 96 МБ) | 64 | один процесс uvicorn с FastAPI и SQLAlchemy занимает около 70–90 МБ, лимит даёт трёхкратный запас. Нагрузка в основном ждёт ввода-вывода от БД, поэтому половины ядра достаточно, а при нехватке масштабируемся числом экземпляров. Ограничение процессов защищает от fork-бомбы |
| `migrate` | 0.5 | 256 МБ | 32 | тот же образ, работает несколько секунд |
| `nginx` | 0.25 | 64 МБ | 64 | один рабочий процесс nginx занимает 5–10 МБ; проксирование почти не нагружает CPU |

**Итого:** не более 2,75 CPU и 1,3 ГБ памяти. Всё окружение работает на
ноутбуке с 4 ГБ ОЗУ рядом с IDE и браузером.

## 5. Масштабирование и балансировка (`nginx/nginx.conf`)

- **Два экземпляра** `app1` и `app2` из одного образа, они отличаются только
  `INSTANCE_ID`.
- **Балансировка** — round-robin. В каждом ответе есть заголовок
  `X-Instance-Id` (его ставит приложение), а в `/healthz` — поле `instance`.
  Заголовок `X-Upstream` добавляет nginx. В журнале nginx записаны
  `upstream=… instance=…`.
- **Отказ экземпляра:**
  - экземпляр, не ответивший два раза за 10 с, исключается из балансировки
    на 10 с (`max_fails=2 fail_timeout=10s`);
  - запрос, который не удалось передать, nginx повторяет на другом экземпляре
    (`proxy_next_upstream error timeout http_502 http_503 http_504`, не
    более 2 попыток за 5 с);
  - `POST`, `PATCH` и `DELETE` повторяются, только если запрос не дошёл до
    приложения. Поэтому операция не выполнится дважды;
  - `proxy_connect_timeout 1s` — недоступный экземпляр быстро распознаётся.
- **Ограничение частоты** — не более 20 запросов/с с одного адреса,
  кратковременный всплеск — до 40. Сверх лимита nginx отвечает `429`, и
  приложение не перегружается.
- Адреса экземпляров в `app_net` фиксированы (`172.30.10.11`, `.12`). Если
  экземпляр остановлен, nginx всё равно запускается и перезапускается: ему не
  нужно разрешать имя через DNS.

**Демонстрация** (шаги 8–10 `make container-check`):

```bash
for i in $(seq 6); do curl -s -D - -o /dev/null http://127.0.0.1:8080/healthz | grep -i x-instance; done
docker compose kill app1          # аварийный отказ
for i in $(seq 6); do curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz; done   # всё 200
docker compose start app1
```

## 6. Что мешает горизонтальному масштабированию

1. **Единственный экземпляр PostgreSQL** — точка отказа и узкое место.
   Экземпляры приложения можно добавлять, но все они пишут в одну базу.
   Масштабирование БД требует реплик только для чтения (отчёты) и
   переключения при отказе (Patroni). Это отдельная инфраструктура.
2. **Соединения с БД.** Каждый экземпляр держит свой пул — до 15 соединений
   (5 постоянных + 10 сверх них). Если поднять 10 экземпляров, получится 150
   соединений, а это больше `max_connections` = 100. Нужен пул соединений
   перед базой (PgBouncer) или меньшие пулы.
3. **Блокировки при списании.** Чтобы не уйти в минус, строка материала
   блокируется (`SELECT … FOR UPDATE`). Корректность от числа экземпляров не
   зависит: блокировка на стороне БД. Но запросы к одному «горячему»
   материалу выполняются строго по очереди, и новые экземпляры их не ускорят.
4. **Миграции.** Их выполняет один разовый контейнер до запуска приложения.
   При обновлении без простоя новая схема должна быть совместима со старой
   версией кода (сначала расширить схему, потом удалить старое). Иначе на
   время обновления придётся остановить все экземпляры.
5. **Лимит частоты считается в памяти одного nginx.** При нескольких
   балансировщиках у каждого свой счётчик, и общий лимит вырастет.
6. **Статический список экземпляров.** Адреса `app1`/`app2` перечислены в
   `nginx.conf` и `docker-compose.yml`. Команда `docker compose up --scale`
   новые экземпляры в балансировку не добавит. Нужно обнаружение сервисов
   (DNS с `resolve` в nginx, оркестратор).
7. **Учётная запись в переменных окружения.** Логин и пароль одинаковы у всех
   экземпляров, и сменить их можно только перезапуском всех экземпляров.
   Состояния сессий нет: HTTP Basic проверяется в каждом запросе. Поэтому
   «липкие» сессии не нужны — это **не** мешает масштабированию.

Чего в приложении **нет** и что масштабированию не мешает:

- состояния в памяти процесса (кэшей, сессий, очередей);
- локальных файлов — корневая ФС только на чтение.

## 7. Запреты (проверяются автоматически)

| Запрет | Где проверяется |
|---|---|
| тег `latest` или образ без тега | `scripts/check_containers.py` (Dockerfile `FROM` и все `image:` в compose) |
| запуск от root | `check_containers.py` (`USER` в Dockerfile, `user:` в compose) и `container-check` шаг 4 (владельцы процессов через `docker top`) |
| секреты в образе | `check_containers.py` (`ENV`/`ARG` с паролями, `.env`/`.git` в контексте сборки) и `container-check` шаг 6 (ENV, история слоёв, файлы образа) |
| отключённый healthcheck | `check_containers.py` (`HEALTHCHECK NONE`, `disable: true`, отсутствие у долгоживущих сервисов) и шаг 3 (все healthy) |
| лишние порты | `check_containers.py` (порты только у nginx и только на конкретном адресе; порт БД — только в dev-файле на 127.0.0.1) и шаг 5 (`docker port`) |

Статическая часть (`make container-lint`) входит в `make verify`. Полная
проверка (`make container-check`) обязательна для любого изменения
`Dockerfile`, `.dockerignore`, `docker-compose*.yml`, `nginx/` — см.
[`workflow.md`](workflow.md).

## 8. Команды

| Команда | Назначение |
|---|---|
| `make lock` | зафиксировать версии зависимостей в `requirements.lock` (закоммитить) |
| `make build` | собрать образ |
| `make up` | поднять всё окружение и дождаться готовности |
| `make ps` / `make logs S=app1` | состояние и журналы |
| `make down` | остановить (том с данными сохраняется) |
| `make container-seed` | демонстрационные данные |
| `make container-lint` | статические запреты |
| `make container-check` | полная проверка (14 шагов) |
| `make restore-new-volume` | восстановление копии в новый том |
| `make dev-db` | только БД с портом на 127.0.0.1 — для `make run` и тестов из `.venv` |
