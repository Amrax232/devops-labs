# Миграции базы данных

Схема базы создаётся и изменяется **только** миграциями Alembic
(`migrations/versions/`). Правка схемы вручную в работающей базе запрещена.

## История изменений схемы

| Ревизия | Файл | Изменение | Особенность |
|---|---|---|---|
| 0001 | `0001_initial_schema.py` | единицы, поставщики, материалы, поступления, строки поступлений | начальная схема, тип `receipt_status` |
| 0002 | `0002_supplier_phone.py` | `suppliers.phone` | необязательная колонка: старые строки получают `NULL` |
| 0003 | `0003_material_location.py` | `materials.location` | **обязательная** колонка в заполненной таблице — нужен `server_default='MAIN'` |
| 0004 | `0004_write_offs.py` | таблица `write_offs` | новая функция «списание»: внешний ключ, `CHECK (quantity > 0)`, индекс |

Ревизии идут строго последовательно (`0001 → 0002 → 0003 → 0004`), у истории
одна вершина — это проверяет `test_migration_history_is_linear`.

## Правила написания миграций

1. **Каждая миграция обратима**: `downgrade()` возвращает схему ровно в
   состояние предыдущей ревизии.
2. **Обязательная колонка в существующей таблице — только со значением по
   умолчанию.** Без `server_default` база не сможет заполнить колонку у уже
   существующих строк, и миграция на рабочей базе упадёт, хотя на пустой
   тестовой пройдёт. Именно эту ошибку ловит
   `test_database_with_data_is_upgraded_without_loss`.
3. **Изменения колонок — через `op.batch_alter_table`.** На PostgreSQL это
   обычный `ALTER TABLE`, а на SQLite, который не умеет большинство
   `ALTER TABLE`, Alembic пересоздаёт таблицу с копированием данных.
4. **Автогенерацию проверяют глазами.** `make makemigration M="..."` создаёт
   черновик, но Alembic не всегда правильно определяет переименования, типы и
   значения по умолчанию.
5. Изменение модели и миграция попадают в **один** merge request.

## Как проверяются миграции

Автоматически — интеграционные тесты на PostgreSQL (`make test-integration`):

| Тест | Что доказывает |
|---|---|
| `test_clean_database_is_created_from_scratch` | пустая база доводится до последней версии |
| `test_database_with_data_is_upgraded_without_loss` | база версии 0002 с данными обновляется до последней без потерь, `location` заполнена `MAIN` |
| `test_every_migration_is_reversible` | «лестница»: каждый шаг вверх → вниз → снова вверх |
| `test_downgrade_to_base_removes_everything` | полный откат удаляет все таблицы и тип `receipt_status` |
| `test_models_match_migrations` | модели в коде совпадают со схемой, которую строят миграции, — если поменяли модель и забыли миграцию, тест упадёт |
| `test_migration_history_is_linear` | одна вершина, не меньше четырёх ревизий |

Вручную на защите — `make migrations-demo` во **временной** базе
`warehouse_migrations_demo` (рабочая не затрагивается). Alembic выполняется
в контейнерной среде — в разовом контейнере `migrate` из образа приложения:

```bash
make up
make migrations-demo
```

В обычной работе миграции применяет тот же контейнер `migrate` при каждом
`make up` (приложение стартует только после его успешного завершения), вручную —
`make container-migrate`.

1. чистая база → `upgrade head` → список таблиц;
2. откат к `0002`, вставка двух материалов «старой» схемы без `location`;
3. `upgrade head` на заполненной базе → материалы на месте, `location = MAIN`.

## Полезные команды

```bash
make migrate                         # применить все миграции к рабочей базе
.venv/bin/alembic current            # текущая версия базы
.venv/bin/alembic history            # история ревизий
.venv/bin/alembic downgrade -1       # откатить последнюю миграцию
make makemigration M="описание"      # черновик новой миграции
```
