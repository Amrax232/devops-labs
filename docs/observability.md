# Наблюдаемость «Складского учёта» (ЛР8)

Журналы, метрики, панель и оповещения: как устроены, где хранятся, как ими
пользоваться при сбое. Что делать по каждому оповещению — [`runbook.md`](runbook.md).

```
 пользователь ──► Nginx :8080 ──┬──► app1 :8000 ──┐
                   │  /grafana/ └──► app2 :8000 ──┴──► PostgreSQL
                   │     │             │ /metrics
                   │     ▼             ▼
 журналы JSON  ◄───┴── Grafana ◄── Prometheus ◄── blackbox (проверки как у пользователя)
 (docker logs)                         ▲    ▲
                          node-exporter    cAdvisor
                          (хост)           (контейнеры)
```

Вся конфигурация — в репозитории (`monitoring/`, `nginx/nginx.conf`,
`docker-compose.yml`) и меняется только через merge request: `make
monitoring-lint` входит в `make verify` и этап CI «Стиль и политика качества».

## 1. Журналы

Одна запись — одна строка JSON в стандартном выводе контейнера (`docker
logs`). Хранение — драйвер `json-file` Docker, не больше 3 файлов по 10 МБ
на контейнер (`docker-compose.yml`, `x-app-common.logging`). Отдельная
система хранения журналов (Loki, ELK) не нужна при двух экземплярах на
одной машине: поиск выполняет `scripts/logs.sh`.

### Поля записи приложения

| Поле | Пример | Назначение |
|---|---|---|
| `time` | `2026-11-05T10:15:02.317+00:00` | время в UTC, миллисекунды |
| `level` | `INFO`, `WARNING`, `ERROR` | уровень |
| `event` | `http_request` | тип события (таблица ниже) |
| `logger` | `app.access` | модуль-источник |
| `message` | `POST /api/v1/receipts/7/post 200` | текст для человека |
| `request_id` | `9f2c…` (32 символа) | идентификатор запроса — общий для Nginx и приложения |
| `instance`, `version` | `app1`, `0.11.0` | экземпляр и версия |
| `method`, `endpoint`, `path` | `POST`, `/api/v1/receipts/{receipt_id}/post` | метод и адрес операции (шаблон маршрута) |
| `status`, `result` | `409`, `client_error` | код ответа и результат: `success`, `client_error`, `server_error` |
| `duration_ms`, `client` | `12.4`, `172.30.10.10` | длительность и источник |

`endpoint` — шаблон маршрута, а не конкретный адрес: поиск «все проведения
поступлений» — один запрос, и в метриках число рядов не растёт с числом
документов. Ошибка 5xx пишется с уровнем `ERROR`, 4xx — `WARNING`.

### Типы событий

| event | Когда |
|---|---|
| `http_request` | каждый запрос (служебные `/healthz`, `/readyz`, `/metrics` — на уровне DEBUG, чтобы не засорять журнал) |
| `unhandled_error` | необработанное исключение (со стеком в поле `exception`) |
| `app_started`, `app_stopped` | запуск и штатная остановка экземпляра |
| `db_unavailable` | база недоступна при сборе метрик |
| `auth_failed` | отказ в доступе (401) |
| `business_rule_violated` | нарушено правило предметной области (409/422) |
| `receipt_posted`, `write_off` | проведено поступление, выполнено списание |
| `http_access` | запись Nginx: `upstream`, `upstream_status`, `instance` — какой экземпляр ответил и были ли повторы |

### Сквозной идентификатор запроса

Nginx создаёт `$request_id` и передаёт его приложению в заголовке
`X-Request-ID`; приложение пишет его во все записи, сделанные при обработке
запроса (`contextvars`), и возвращает клиенту в ответе. Пользователь
сообщает идентификатор из ответа — `make logs-find ID=<id>` показывает
путь запроса: Nginx → экземпляр → ошибка. Идентификатор, присланный
клиентом при прямом обращении к экземпляру, принимается, только если он
из безопасных символов (до 64 знаков), иначе создаётся новый.

### Секреты в журнал не попадают

Каждое строковое поле записи перед выводом проходит маскирование
(`app/logging_setup.py`):

- настоящие значения пароля API и пароля базы из настроек экземпляра;
- типичные формы: `password=…`, `"token": "…"`, `Authorization: Basic …`,
  пароль в строке подключения `scheme://user:пароль@host`, токены GitHub.

Значение заменяется на `***`, имя поля остаётся (видно, *что* пытались
записать). Каждое срабатывание увеличивает
`warehouse_log_secrets_redacted_total` → оповещение `SecretRedactedInLogs`:
маскирование — страховка, а запись секрета — ошибка в коде. Nginx не пишет
строку запроса (`$args`) и заголовки. Секрет, выведенный в обход журнала
(`print()`), находит `make logs-secrets` — проверка всех журналов на
настоящие значения паролей из `.env` и типичные формы секретов; она же
выполняется в `make container-check` (шаг 15).

### Поиск

```bash
make logs-find LEVEL=ERROR SINCE=30m          # ошибки за 30 минут
make logs-find ID=9f2c...                      # один запрос насквозь
make logs-find EVENT=http_request CODE=5       # ответы 5xx
make logs-find EVENT=auth_failed S=app1,app2   # отказы в доступе
make logs-find TEXT='база' N=20                # по тексту сообщения
./scripts/logs.sh --json -t 10m | jq 'select(.duration_ms > 500)'   # медленные запросы
make logs-secrets                              # нет ли секретов в журналах
```

## 2. Метрики

### Приложение (`GET /metrics` каждого экземпляра, `app/metrics.py`)

| Метрика | Тип | Что показывает |
|---|---|---|
| `warehouse_http_requests_total{method, endpoint, status}` | counter | запросы; ошибки — те же ряды со status 4xx/5xx |
| `warehouse_http_request_duration_seconds{method, endpoint}` | histogram | время ответа (корзины 5 мс … 10 с) |
| `warehouse_http_requests_in_progress` | gauge | запросы в обработке |
| `warehouse_app_info{version, revision, instance, environment}` | gauge = 1 | какая версия работает |
| `warehouse_database_up` | gauge | база доступна (1) или нет (0) — проверка `SELECT 1` при сборе |
| `warehouse_materials_below_min` | gauge | **предметная**: позиций ниже минимального остатка |
| `warehouse_materials_total` | gauge | материалов в справочнике |
| `warehouse_stock_operations_total{operation}` | counter | **предметная**: проведённые поступления и списания |
| `warehouse_auth_failures_total` | counter | отказы в доступе |
| `warehouse_log_secrets_redacted_total` | counter | замаскированные секреты в журнале |

Через Nginx `/metrics` недоступен (404): метрики собирает Prometheus во
внутренней сети.

### Инфраструктура

| Источник | Что даёт |
|---|---|
| **blackbox-exporter** | `probe_success`, время ответа: `/healthz` и `/readyz` через Nginx (как у пользователя) и `/readyz` каждого экземпляра |
| **node-exporter** | хост: CPU, память, диск (`node_filesystem_avail_bytes`), сеть |
| **cAdvisor** | контейнеры: CPU, память и её лимит, время старта (перезапуски), события OOM |
| Prometheus | `up` — удалось ли собрать метрики цели |

cAdvisor читает метрики контейнеров из cgroups хоста. В Docker Desktop
(Windows/macOS) Docker работает в отдельной виртуальной машине, и метрики
контейнеров могут отсутствовать; на серверах Debian (staging, production)
и в Docker Engine внутри WSL они есть.

### Сбор и хранение

Prometheus v2.55.1: опрос каждые 15 с, правила — каждые 15 с, хранение
15 дней и не больше 1 ГБ (том `prometheus_data`). Порт наружу не
опубликован: запросы — `make metrics-query Q='…'` (из контейнера Prometheus)
или Grafana → Explore.

## 3. Панель Grafana

`http://127.0.0.1:8080/grafana/` (на серверах — `http://<адрес>:<порт>/grafana/`),
вход `admin` / `GRAFANA_ADMIN_PASSWORD` (локально — `.env`, на серверах —
`ansible-vault`). Регистрация и анонимный доступ выключены. Источник данных
и панель загружаются из репозитория (`monitoring/grafana/`); правка через
интерфейс не сохраняется — изменения только через merge request.

Панель «Складской учёт — обзор» (`/grafana/d/warehouse-overview`):

| Раздел | Панели |
|---|---|
| Состояние | доступен пользователям, готов (база), экземпляров, версия, активные оповещения, ниже минимума |
| Нагрузка, ошибки, время ответа | запросы в секунду по экземплярам; ошибки 5xx и 4xx в %; p50/p95/p99; запросы по адресам и кодам; 5 самых медленных адресов |
| Ресурсы | память контейнеров в % лимита, CPU контейнеров, хост (диск, память, CPU), перезапуски |
| Предметная область и безопасность | складские операции за час, материалы и позиции ниже минимума, отказы в доступе и замаскированные секреты, сработавшие оповещения |

## 4. Оповещения

Правила — `monitoring/prometheus/rules/warehouse.yml`, у каждого: условие,
время, в течение которого оно должно держаться (`for`, чтобы не реагировать
на единичный сбой), важность, описание и раздел инструкции.

| Оповещение | Условие | Важность | Раздел |
|---|---|---|---|
| `WarehouseUnavailable` | `/healthz` через Nginx не проходит 1 мин | critical | [1](runbook.md#1-сервис-недоступен) |
| `WarehouseNotReady` | `/readyz` (Nginx или экземпляр) ≠ 200 1 мин | critical | [2](runbook.md#2-база-данных-недоступна) |
| `WarehouseInstanceDown` | метрики экземпляра не собираются 1 мин | warning | [4](runbook.md#4-экземпляр-перезапускается-или-остановлен) |
| `DatabaseUnavailable` | `warehouse_database_up` = 0 у всех экземпляров 30 с | critical | [2](runbook.md#2-база-данных-недоступна) |
| `HighErrorRate` | 5xx > 5% запросов 2 мин | critical | [6](runbook.md#6-ошибка-новой-версии) |
| `SlowResponses` | p95 > 1 с 5 мин | warning | [5](runbook.md#5-нехватка-памяти-или-ресурсов) |
| `ContainerRestarted` | контейнер стартовал заново за 10 мин | warning | [4](runbook.md#4-экземпляр-перезапускается-или-остановлен) |
| `ContainerMemoryNearLimit` | память > 90% лимита 2 мин | warning | [5](runbook.md#5-нехватка-памяти-или-ресурсов) |
| `DiskSpaceLow` | свободно < 10% диска хоста 1 мин | critical | [3](runbook.md#3-нехватка-места-на-диске) |
| `SecretRedactedInLogs` | замаскирован секрет в журнале | critical | [9](runbook.md#9-утечка-секрета-в-журнал) |
| `AuthFailuresBurst` | > 20 отказов в доступе за 5 мин | warning | [7](runbook.md#7-нарушение-прав-доступа) |
| `MaterialsBelowMinimum` | есть позиции ниже минимума 15 мин | info | [10](runbook.md#10-предметные-оповещения) |

Доля ошибок считается только по 5xx: ответы 4xx — неверный ввод
пользователя, а не сбой сервиса (это проверено отдельным тестом правила).

Сработавшие оповещения видны в Grafana (панель «Активные оповещения» и
таблица), в `make alerts` и `make status`. Доставка уведомлений (почта,
мессенджер через Alertmanager) в учебном стенде не настраивается: правила
и их проверка от неё не зависят, Alertmanager подключается одной секцией
`alerting` в `prometheus.yml`.

## 5. Проверки конфигурации

| Проверка | Что ловит |
|---|---|
| `make monitoring-lint` → `scripts/check_monitoring.py` | у правила нет severity/описания/раздела инструкции; раздела нет в `runbook.md`; **нет теста, в котором оповещение срабатывает**; метрика `warehouse_*` в правиле или на панели не объявлена в `app/metrics.py` (опечатка → правило никогда не сработает); на панели нет обязательного раздела |
| `make monitoring-lint` → `promtool check config` | синтаксис `prometheus.yml` и правил |
| `make monitoring-lint` → `promtool test rules` | unit-тесты правил: на заданных рядах оповещение срабатывает в нужный момент и не срабатывает раньше или на 4xx (`monitoring/prometheus/tests/`) |
| `make monitoring-lint` → blackbox `--config.check` | конфигурация проверок доступности |
| `tests/unit/test_logging.py`, `tests/api/test_observability.py` | формат записей, маскирование и счётчик, `request_id`, метрики запросов и предметные метрики |
| `make container-check`, шаг 15 | в работающем окружении: все цели сбора up, правила загружены, Grafana через Nginx с панелью, без входа — 401, `/metrics` снаружи 404, запрос прослеживается по `request_id`, журналы — JSON с полями, секретов в журналах нет |
| `make infra-verify` (роль `verify`) | на серверах: Grafana через Nginx, все цели сбора up, `/metrics` — 404 |

## 6. Безопасность мониторинга

- Наружу открыт только Nginx; Prometheus, Grafana, экспортёры — во
  внутренней сети `monitoring` (`internal: true`). Grafana — только через
  Nginx и только со входом.
- Все сервисы мониторинга работают не от root, с корневой ФС только для
  чтения, без capabilities, с ограничениями памяти, CPU и числа процессов.
  **Исключение — cAdvisor**: читает cgroups и сведения Docker о контейнерах.
  Доступ только на чтение (`/sys`, `/var/run`, корень хоста), портов нет,
  метки и переменные окружения контейнеров в метрики не выгружаются
  (пароли из `environment` туда не попадут).
- Пароль Grafana: локально — `.env` (не в git), в CI — случайный
  (`scripts/ci_env.sh`), на серверах — `ansible-vault`
  (`vault_warehouse_grafana_admin_password`).

## 7. Выпуск с наблюдением

Состояние системы до и после выпуска фиксируется в файл:

```bash
make release-snapshot NAME=before     # reports/release-before-<время>.md
# … выпуск …
make release-snapshot NAME=after
diff reports/release-before-*.md reports/release-after-*.md
```

В снимке: контейнеры с образами и перезапусками, доступность и версия,
цели сбора метрик, оповещения, запросы в секунду, доля ошибок, p95,
состояние базы, предметная метрика, память контейнеров, ошибки в журналах.
На сервере — `scripts/obs.sh snapshot <имя>` из файлов выпуска
(`runbook.md`, начало).

## 8. Барьеры: что не даёт ошибке дойти до пользователей

**Автоматические** — срабатывают без участия человека:

| Этап | Барьер |
|---|---|
| Локально | `make verify` (11 шагов): политика, секреты, линтер, SAST, уязвимости зависимостей, запреты для контейнеров, **конфигурация мониторинга**, тесты с порогом покрытия, мутационное тестирование |
| Merge request | CI (`ci.yml`): те же проверки + миграции, копия/восстановление, контейнерная среда (`container-check`, в т. ч. наблюдаемость), проверка релиза, анализ образа; `ci-gate` — обязательная проверка ветки `main` |
| Выпуск в staging | `deploy.sh`: обязательные настройки, образ только из реестра, копия базы, healthcheck, проверка версии и сценария; провал — автоматический возврат прежней версии |
| Инфраструктура | `Infrastructure CI`: ansible-lint, синтаксис, требования; после применения — идемпотентность и роль `verify` |
| Работа | оповещения Prometheus по доступности, ошибкам, времени ответа, ресурсам, диску, безопасности; Nginx исключает неответивший экземпляр |

**Организационные** — решение принимает человек:

| Барьер | Где закреплён |
|---|---|
| Изменение только через задачу → ветку → merge request; прямой push в `main` запрещён | `docs/workflow.md`, защита ветки (`scripts/setup_github.sh`) |
| Обязательное согласование владельцами критических файлов (CI, развёртывание, инфраструктура, мониторинг) | `.github/CODEOWNERS` |
| Выпуск в production и применение инфраструктуры — после подтверждения | окружения GitHub с Required reviewers (`infra-production`) |
| В production — только версия, прошедшая staging | `docs/cd.md`, `docs/infra.md` |
| Снимок состояния до и после выпуска; решение «оставить или откатить» | этот раздел, `make release-snapshot` |
| Разбор каждого инцидента с улучшением процесса | `docs/incidents/` |
