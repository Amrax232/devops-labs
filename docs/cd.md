# Непрерывная поставка (CD) и проверка работающего релиза

**Успешная сборка не равна успешному выпуску.** Версия принимается, только
если она проверена в целевой среде — тестовом окружении `staging`, которое
повторяет боевую конфигурацию.

## 1. Тестовое окружение

```
GitHub Actions ──(задание CD, исходящее HTTPS)──┐
  CI: тесты → образ → ghcr.io                   │
                                                ▼
                    ВМ warehouse-stage 192.168.56.20 (Debian 12, VirtualBox)
                    ┌──────────────────────────────────────────────────────┐
                    │ actions-runner (служба, пользователь deploy)         │
                    │   └─ deploy/stage/deploy.sh                          │
                    │ /opt/warehouse-stage                                 │
                    │   env/stage.env     настройки окружения (600)        │
                    │   releases/<коммит> compose-файлы и nginx.conf       │
                    │   current →         работающий выпуск                │
                    │   state/            текущая версия, стек, история    │
                    │   backups/          копии БД перед выпуском          │
                    │ docker compose -p warehouse-stage:                   │
                    │   db, migrate, app1, app2, nginx :8080               │
                    └──────────────────────────────────────────────────────┘
```

- **Отдельная машина.** ЛР2 (`warehouse-app`, `warehouse-db`) не
  затрагивается. В тестовом окружении своя база (том
  `warehouse-stage_db_data`) и свои пароли.
- **Та же конфигурация, что в CI.** Используются `docker-compose.yml` и
  `nginx.conf` из того же коммита, что и образ. На сервер добавляется только
  `docker-compose.deploy.yml` — образ из реестра вместо сборки.

## 2. Доступ pipeline к серверу

На сервере работает GitHub runner (self-hosted, метка `staging`) под
**отдельной учётной записью `deploy`**:

- системный пользователь без пароля и без входа по SSH (`AllowUsers` —
  только администратор `deployer`);
- нет sudo, единственная дополнительная группа — `docker`. Группа `docker`
  по силе равна root на этой машине, поэтому на ней нет ничего, кроме
  тестового окружения;
- runner сам забирает задания по исходящему HTTPS. Машине не нужен внешний
  IP, а входящих подключений из интернета нет;
- runner выполняет только задание развёртывания. Чужой код на нём не
  запускается:
  - в `deploy.yml` нет событий `push` и `pull_request`;
  - автоматический запуск — только после успешного CI по `push` в `main`
    этого репозитория (проверяются `event`, `head_branch`,
    `head_repository`);
  - запуски из форков требуют одобрения (`scripts/setup_staging.sh`);
  - `make policy` не пропустит задание на self-hosted runner с событиями
    `push` или `pull_request` либо без окружения `staging`.

**Реестр.** Задание входит в `ghcr.io` с `GITHUB_TOKEN`, у которого есть
только право `packages: read`, и выходит в конце задания.

## 3. Образ из реестра, настройки — отдельно

- **Образ не пересобирается.** В `docker-compose.deploy.yml` у
  `migrate`/`app1`/`app2` удалена секция `build` (`!reset`) и задано
  `pull_policy: never`. `deploy.sh` скачивает образ (`docker pull`) и
  запускает `docker compose up --no-build`. Если образа нет, выпуск падает, а
  не собирает образ на сервере. Это проверяет и `make container-lint`.
- **Тег — это коммит.** В реестре теги `<SHA>`, `sha-<SHA7>` и
  `<версия>-<SHA7>`, `latest` запрещён. Из метки образа
  `org.opencontainers.image.revision` `deploy.sh` узнаёт коммит и берёт из
  него compose-файлы и `nginx.conf` (`git archive`). Конфигурация всегда
  соответствует образу, в том числе при возврате старой версии.
- **Настройки окружения хранятся на сервере**, в
  `/opt/warehouse-stage/env/stage.env` (права 600, владелец `deploy`):
  - адрес реестра, логин и пароль API, параметры PostgreSQL, адрес и порт
    Nginx, `AUTO_ROLLBACK`;
  - в репозитории — только шаблон `deploy/stage/stage.env.example`;
  - в образе настроек нет, один и тот же образ работает в CI и в staging.

## 4. Когда развёртывается

| Запуск | Что разворачивается | Ограничение |
|---|---|---|
| автоматически после успешного CI по push в `main` | образ этого коммита (тег = SHA) | только `main`; CI успешен, значит образ опубликован |
| вручную: Actions → CD (staging) → Run workflow, `deploy` | указанный тег (или последний коммит `main`) | окружение `staging` разрешено только для защищённой ветки `main` |
| вручную, `rollback` | предыдущая успешная версия | то же |
| вручную, `status` | ничего — показывает состояние | — |

**Ручное подтверждение** включается командой
`./scripts/setup_staging.sh --approve <логин>`. Тогда каждый выпуск ждёт
кнопки Approve в GitHub (Required reviewers окружения `staging`).

**Одновременные развёртывания исключены дважды:**

- `concurrency: deploy-staging` с `cancel-in-progress: false` — второй запуск
  ждёт первый, начатый выпуск не прерывается;
- `flock` в `deploy.sh` — это защищает и от ручного запуска на сервере во
  время работы CD.

## 5. Порядок выпуска (`deploy/stage/deploy.sh`)

1. **Блокировка** (`flock`, ожидание до 10 минут).
2. **Настройки.** Все обязательные переменные из `stage.env` должны быть
   заданы. Если чего-то нет, выпуск не начинается, а прежняя версия
   продолжает работать.
3. **Образ.**
   - `docker pull`. Если тега нет, ошибка сразу; если реестр недоступен —
     3 попытки с паузой. Прежняя версия не затрагивается;
   - коммит определяется по метке образа;
   - из этого коммита берутся файлы выпуска.
4. **Копия БД** перед выпуском (`backups/pre-deploy-*.dump`, хранятся 5).
5. **Переключение** — `docker compose up -d --no-build`. Миграции выполняет
   контейнер `migrate` нового выпуска.
6. **Проверка выпуска:**
   - все контейнеры healthy, `migrate` завершился с кодом 0
     (`scripts/compose_wait.sh`);
   - `app1` и `app2` запущены именно из разворачиваемого образа;
   - `scripts/smoke_test.sh` через Nginx проверяет:
     - `/healthz`;
     - `/readyz` (база доступна);
     - `/version` — коммит совпадает с образом;
     - изменение без входа — 401;
     - **основной сценарий**: единица, поставщик, материал → поступление →
       проведение → остаток 5 → списание 2 → остаток 3 → списать больше
       остатка нельзя (422) → отчёт по остаткам.
7. **Итог:**
   - **все проверки пройдены** — версия записывается как текущая
     (`state/current_tag`, стек `state/stack`, история `state/history.tsv`);
   - **любая проверка не пройдена** — выпуск **не считается успешным**:
     задание CD завершается с ошибкой, в историю пишется `FAILED`. Затем
     автоматически возвращается предыдущая версия (`AUTO_ROLLBACK=1`) и
     проверяется тем же сценарием.

В Summary запуска выводятся итог, тег и версия, которая работает сейчас.

## 6. Развёртывание конкретного тега и возврат версии

```text
Actions → CD (staging) → Run workflow → action: deploy, tag: sha-1a2b3c4
Actions → CD (staging) → Run workflow → action: rollback
```

То же на сервере — от имени `deploy`, из рабочей копии runner, с тем же
`deploy.sh` (для приватного пакета перед этим нужен `docker login ghcr.io`):

```bash
cd /opt/actions-runner/_work/<репозиторий>/<репозиторий>
sudo -u deploy ./deploy/stage/deploy.sh status
sudo -u deploy ./deploy/stage/deploy.sh deploy sha-1a2b3c4
sudo -u deploy ./deploy/stage/deploy.sh rollback
```

**Возврат** снимает текущую версию со стека успешных выпусков и разворачивает
предыдущую. Повторный возврат уходит ещё на шаг назад.

**Схема БД при возврате не откатывается** (`deploy/stage/rollback.yml`):

- миграции пишутся совместимыми назад — сначала расширить схему, а старое
  удалять отдельным выпуском, поэтому предыдущая версия работает на текущей
  схеме;
- контейнер `migrate` предыдущей версии ничего не применяет: он не знает
  новых ревизий и упал бы на `alembic upgrade head`;
- если схему всё же нужно вернуть, используется копия, снятая перед выпуском.

## 7. Сбои и их обработка

| Ситуация | Как имитировать | Что происходит |
|---|---|---|
| неверный тег | `tag: no-such-tag` | `manifest unknown` → выпуск не начат, работает прежняя версия |
| отсутствующая переменная | `simulate: missing-var` (или убрать строку из `stage.env`) | «не заданы переменные окружения: AUTH_PASSWORD» → выпуск не начат |
| неуспешный healthcheck | `simulate: healthcheck` | контейнеры unhealthy → выпуск не принят → автоматический возврат |
| приложение запускается, но основной сценарий не работает | `simulate: scenario` (неверная конфигурация экземпляров) | healthcheck зелёный, но smoke-тест падает на создании данных (401) → выпуск не принят → возврат |
| недоступный реестр | `simulate: registry` (адрес `registry.invalid`) | 3 попытки `docker pull` → выпуск не начат |
| возврат предыдущей версии | `action: rollback` | предыдущая успешная версия + та же проверка |

Имитация доступна только при ручном запуске. При автоматическом запуске
после CI она всегда отключена.

## 8. Первоначальная настройка

На хосте:

1. Создать ВМ Debian 12 по шаблону ЛР2 (2 ГБ ОЗУ, 2 CPU, адаптеры NAT и
   «виртуальная сеть хоста»), адрес `192.168.56.20`
   (`deploy/common/interfaces.example`).
2. Скопировать на ВМ каталог `deploy/` репозитория.

На ВМ от root:

```bash
bash deploy/common/00-base-setup.sh stage            # затем ключ SSH, systemctl restart ssh
bash deploy/stage/10-install-docker.sh
bash deploy/stage/20-deploy-user.sh ghcr.io/<владелец-в-нижнем-регистре>/warehouse-inventory
bash deploy/stage/40-firewall-stage.sh
```

В WSL, в репозитории:

```bash
./scripts/setup_staging.sh               # владельцы deploy/, окружение staging, переменная, токен runner
# необязательно — ручное подтверждение: ./scripts/setup_staging.sh --approve <логин>
git add .github/CODEOWNERS && git commit -m "chore: владельцы deploy/"   # make policy требует владельца deploy/
```

На ВМ от root — регистрация runner токеном из предыдущего шага:

```bash
bash deploy/stage/30-github-runner.sh https://github.com/<владелец>/<репозиторий> <токен>
```

Проверка — в Settings → Actions → Runners runner `warehouse-stage` в
статусе Idle. Первое развёртывание — Actions → CD (staging) → Run workflow.
