# Регламент внесения и приёмки изменений

Документ обязателен для всех участников команды. Основной принцип курса:
**любое изменение считается потенциально ошибочным**, поэтому попадает в `main`
только после автоматических и организационных проверок.

## 1. Ветки

| Ветка | Назначение |
|---|---|
| `main` | защищённая ветка, всегда рабочее состояние, только через merge request |
| `feature/<id задачи>-<краткое-имя>` | новая функциональность |
| `fix/<id задачи>-<краткое-имя>` | исправление ошибки |
| `docs/<краткое-имя>` | изменения только в документации |

Прямые коммиты и `push --force` в `main` запрещены — и не только правилом:
защита ветки на GitHub (`scripts/setup_github.sh`) технически не даёт этого
сделать никому, включая администраторов.

## 2. Порядок работы над изменением

1. **Задача.** Создать issue: что делаем, зачем, как проверить результат.
2. **Ветка.** `git switch -c feature/12-material-search` от актуального `main`.
3. **Коммиты.** Небольшие, осмысленные, в формате
   `<тип>: <что сделано>` (`feat:`, `fix:`, `docs:`, `test:`, `chore:`).
   Один коммит — одна законченная мысль, не «фикс фикса».
4. **Локальная проверка.** `make verify` — обязательно до отправки. Это те же
   команды, что выполнит CI ([`ci.md`](ci.md)); весь pipeline локально — `make ci`.
5. **Merge request.** В описании: ссылка на задачу, что изменено, как проверялось,
   отдельно отмечены изменения критических файлов.
6. **Ревью.** Минимум один участник команды, кроме автора. Ревьюер проверяет
   соответствие задаче, тесты на новое поведение и отсутствие секретов в диффе.
7. **CI.** Pipeline запускается сам при `push` и при создании merge request.
   Обязательная проверка `ci-gate` должна быть зелёной.
8. **Слияние.** После одобрения и зелёного `ci-gate`; ветка удаляется. После
   слияния CI на `main` публикует образ с тегом по commit SHA.

## 3. Обязательные команды проверки

| Команда | Что проверяет |
|---|---|
| `make verify` | **весь обязательный набор**: политика, секреты, линтер, SAST, тесты всех уровней с покрытием, мутационное тестирование |
| `make test` | быстрая проверка во время работы: unit + API |
| `make lint` / `make sast` | отдельно стиль и безопасность кода |
| `make container-check` | **обязательна при изменении контейнерной среды**: сборка, запуск, пользователи, сети, секреты, балансировка, отказ экземпляра, SIGTERM, сохранность данных, восстановление в новый том — [`containers.md`](containers.md) |

`make verify` должен проходить локально до создания merge request и повторяться
после каждого изменения по замечаниям ревью. Вывод `make verify` прикладывается
к описанию merge request.

**Контейнерная среда** (`Dockerfile`, `.dockerignore`, `docker-compose*.yml`,
`nginx/`) меняется только через merge request, к которому приложен вывод
успешного `make container-check`. Без этого ревьюер изменение не одобряет.
Пункт об этом есть в шаблоне merge request, и убрать его не даёт `make policy`. Состав шагов и пороги — [`quality-policy.md`](quality-policy.md).

## 4. Запрещённые действия

Полный перечень с автоматической проверкой — [`quality-policy.md`](quality-policy.md).

- удалять или помечать «пропущенными» тесты, чтобы проверка прошла;
- отключать правила линтера, снижать пороги качества, ослаблять проверки;
- коммитить `.env`, пароли, ключи, дампы базы и содержимое `backups/`;
- вносить изменения в `main` напрямую, переписывать историю `main`;
- менять схему базы данных вручную вместо миграции;
- сливать merge request без ревью и без прохождения проверок;
- добавлять код, который участник не может объяснить на защите.

## 5. Критические файлы

Список — в [`.github/CODEOWNERS`](../.github/CODEOWNERS): тесты, `Makefile`,
настройки анализаторов (`pyproject.toml`, `.gitleaks.toml`, `security/`),
`scripts/`, pipeline (`.github/`), зависимости, Dockerfile и compose, миграции,
`app/config.py`, `app/security.py`, `.env.example`, `.gitignore`.

Изменение такого файла:

- нельзя влить без одобрения владельца (Require review from Code Owners);
- автоматически попадает в отчёт «Критические файлы» merge request, удаление
  теста отмечается как ошибка;
- отдельно перечисляется в описании merge request.

## 6. Работа с секретами

- Секреты хранятся только в локальном `.env`, который исключён `.gitignore`.
- В репозитории лежит `.env.example` без реальных значений.
- При случайном попадании секрета в историю: немедленно сменить значение,
  сообщить команде, вычистить историю отдельным согласованным изменением.
- Проверка: `git ls-files .env` не должна ничего выводить (входит в `make verify`).

## 7. Порядок приёмки изменения

Изменение считается принятым, если одновременно выполнено:

1. есть связанная задача;
2. `make verify` проходит без ошибок локально, а `ci-gate` — в CI;
3. новое поведение закрыто тестом (или в MR объяснено, почему тест не нужен);
4. документация (`README.md`, `docs/`) обновлена, если менялось поведение или API;
5. merge request одобрен хотя бы одним участником, кроме автора, а при
   изменении критических файлов — их владельцем;
6. изменения критических файлов явно перечислены в описании MR.

## 8. Разрешение конфликтов слияния

1. Обновить свою ветку: `git fetch origin && git merge origin/main`.
2. Разобрать конфликт вручную, сохранив обе содержательные правки; выбор
   «оставить только своё» без обсуждения не допускается.
3. После разрешения — снова `make verify`.
4. В коммите слияния описать, какие изменения были объединены и почему.

## 9. Релизы

- Версии — семантические: `vMAJOR.MINOR.PATCH`.
- Тег ставится на коммит в `main` после прохождения проверок:
  `git tag -a v0.1.0 -m "Лабораторная работа №1" && git push origin v0.1.0`.
- Каждая версия описывается в `CHANGELOG.md`.
