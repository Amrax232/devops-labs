# Непрерывная интеграция (CI)

CI — независимый и обязательный барьер перед сборкой и публикацией образа.
Изменение попадает в `main`, а образ — в реестр, только если на сервере CI
пройдены все обязательные проверки. Локальный `make verify` разработчика
этого не заменяет.

- **Система:** GitHub Actions.
- **Pipeline:** [`.github/workflows/ci.yml`](../.github/workflows/ci.yml).
- **Реестр образов:** GitHub Container Registry (`ghcr.io`).

## 1. Когда запускается

| Событие | Что происходит |
|---|---|
| `push` в любую ветку | этапы 1–6 |
| `pull_request` в `main` (создание и каждое обновление) | этапы 1–6 и отчёт «Критические файлы» |
| `push` в `main` (слияние merge request) | этапы 1–6 и публикация образа (этап 7) |
| вручную (`workflow_dispatch`) | этапы 1–6 |

Запуски одной ветки не накапливаются: новый отменяет предыдущий
(`concurrency`). На `main` предыдущий запуск не отменяется.

## 2. Этапы

```
1. стиль и политика ─┬─ 2. тесты ─────────────┐
                     ├─ 3. миграции ──────────┤
                     ├─ 4. резервные копии ───┼─ 6. контейнеры ── 7. публикация (только main)
                     └─ 5. безопасность ──────┘
ci-gate — итог: успешен, только если успешны этапы 1–6
```

| Этап | Команды | Отчёты (артефакты запуска) |
|---|---|---|
| 1. Стиль и политика качества | `make policy`, `make lint`, `make container-lint` | — |
| 2. Тесты | `make test-db`, `make coverage`, `make mutation` | `reports-tests`: `junit.xml`, `coverage.xml`, `coverage-html/`, `mutation.txt` |
| 3. Миграции | `make dev-db`, `make migrations-check` | журнал этапа |
| 4. Резервное копирование | `make backup-check` | журнал этапа |
| 5. Безопасность | `make secrets`, `make secrets-scan`, `make sast`, `make deps-audit` | `reports-security`: `gitleaks.json`, `bandit.json`, `pip-audit.json` |
| 6. Контейнерная проверка и анализ образа | `make container-check`, `make image-scan` | `reports-container`: `trivy.txt`; артефакт `image` — проверенный образ |
| 7. Публикация образа | `make publish` | теги образа в реестре |

**Каждый этап вызывает только make-цели.** Это те же команды, которые
разработчик запускает у себя:

- `make verify` — проверки этапов 1, 2 и 5;
- `make ci` — весь pipeline в том же порядке.

Поэтому локальная и серверная проверки совпадают не по договорённости, а по
построению. Если бы CI проверял что-то своё, могло бы случиться одно из двух:

- изменение, прошедшее локально, падает на сервере, и разработчик не может
  воспроизвести ошибку;
- сервер пропускает то, что ловится локально, и барьер перестаёт быть барьером.

Версии инструментов тоже одинаковые:

- Python-пакеты ставятся из `requirements.lock` (`make setup`);
- сканеры запускаются из Docker-образов с закреплёнными версиями
  (`zricethezav/gitleaks:v8.21.2`, `aquasec/trivy:0.56.2`).

## 3. Отдельная тестовая база

- Каждое задание работает со своей новой PostgreSQL (`make dev-db` на
  раннере), которая исчезает вместе с раннером.
- Интеграционные тесты используют отдельную базу `warehouse_test`
  (`make test-db`). На базе, имя которой не оканчивается на `_test`, они
  запускаться отказываются (`tests/integration/conftest.py`).
- Проверка миграций идёт в отдельной базе `warehouse_migrations_check`, она
  удаляется после проверки.
- Демонстрация восстановления работает с базой этапа 4. У каждого этапа своя
  база, и этапы не мешают друг другу.

## 4. Кэширование

| Что | Как |
|---|---|
| пакеты pip | `actions/setup-python` с `cache: pip`. Ключ — хэш `requirements*.txt` и `requirements.lock`, кэш сбрасывается при изменении зависимостей |
| база уязвимостей trivy | `actions/cache`, каталог `~/.cache/trivy` |
| слои Docker | внутри задания: `make container-check` и `make image-scan` используют образ, собранный на шаге сборки |

## 5. Образ: теги и публикация

- **Тег связан с коммитом.** В CI образ собирается под тегом
  `warehouse-inventory:<версия>-<7 символов SHA>`, например `0.7.0-3f2a9c1`
  (`scripts/ci_env.sh`). В метках образа есть полный SHA
  (`org.opencontainers.image.revision`) и адрес репозитория.
- **Публикуется проверенный образ.** На этапе 6 тот же образ проходит
  `make container-check` и `make image-scan`, затем сохраняется в
  `dist/image.tar` и передаётся этапу 7 артефактом. Этап 7 образ не
  пересобирает: в реестр уходит ровно то, что проверено.
- **Теги в реестре:** `ghcr.io/<владелец>/warehouse-inventory:<полный SHA>`,
  `:sha-<7 символов>`, `:<версия>-<7 символов>`. Тега `latest` нет: по тегу
  всегда видно, из какого коммита собран образ.
- **Публикация запрещена при ошибке.** Это обеспечивают четыре механизма:
  - этап 7 зависит (`needs`) от всех этапов 1–6. Если любой из них упал или
    отменён, GitHub пропускает этап 7 (статус «skipped»), и образ не
    публикуется;
  - первым шагом этап 7 ещё раз проверяет результаты всех этапов;
  - публикация идёт только при `push` в `main`. Из веток и merge request
    образ не публикуется;
  - этап 7 работает в окружении `registry`, а оно разрешено только для
    защищённой ветки. Право записи в реестр (`packages: write`) есть только у
    этого этапа, у остальных — только чтение.

## 6. Секреты

| Секрет | Где хранится | Для чего |
|---|---|---|
| `CI_AUTH_PASSWORD` | Settings → Secrets and variables → Actions | пароль API в тестах и контейнерах |
| `CI_POSTGRES_PASSWORD` | там же | пароль PostgreSQL на раннере |
| `GITHUB_TOKEN` | выдаётся GitHub на время запуска | вход в `ghcr.io` на этапе публикации |

- Секреты создаёт `scripts/setup_github.sh`: случайные значения, которые
  никто не видит.
- `scripts/ci_env.sh` собирает из `.env.example` и секретов файл `.env`
  (права 600). Значения секретов GitHub маскирует в журналах.
- Секреты недоступны запускам из чужих форков.

## 7. Анализаторы безопасности

| Проверка | Инструмент | Что запрещено |
|---|---|---|
| секреты в истории git | gitleaks (стандартные правила + `.gitleaks.toml`) | любая находка. Исключены только учебные заглушки (`warehouse123`, `test-password`) |
| секретные файлы под контролем версий | `scripts/check_secrets.sh` | `.env`, ключи, дампы |
| код приложения | bandit | находки среднего уровня и выше |
| зависимости | pip-audit по `requirements.lock` | любая известная уязвимость без оформленного исключения |
| образ | trivy (ОС и Python-пакеты образа) | CRITICAL, для которых есть исправление. HIGH и CRITICAL — в отчёте `trivy.txt` |
| конфигурация контейнеров | `scripts/check_containers.py` | `latest`, root, секреты, отключённый healthcheck, лишние порты |

**Исключения для уязвимостей** —
[`security/vulnerability-exceptions.toml`](../security/vulnerability-exceptions.toml).
У каждого исключения обязательны:

- идентификаторы уязвимости;
- обоснование, почему её нельзя эксплуатировать в этом приложении;
- срок пересмотра, не дальше 180 дней.

После срока падают `make policy` и `make deps-audit`. Одно и то же исключение
действует и для pip-audit, и для trivy.

Секрет, однажды попавший в историю, остаётся в ней и после удаления строки,
поэтому gitleaks продолжит его находить. Такой секрет считается
скомпрометированным: его меняют, а ветку не сливают.

## 8. Защита критических файлов

Критические файлы приёмки:

- тесты;
- `Makefile`, `pyproject.toml`, `.gitleaks.toml`, `security/`, `scripts/`;
- pipeline и шаблоны (`.github/`);
- зависимости;
- Dockerfile и compose;
- миграции;
- `app/config.py`, `app/security.py`.

Полный список — [`.github/CODEOWNERS`](../.github/CODEOWNERS).

Защита устроена в пять уровней. Ослабить проверку можно только в
merge request, где это увидят и где нужно согласие владельца:

1. **Защита ветки `main`** (`scripts/setup_github.sh`):
   - изменения — только через merge request;
   - обязательная проверка `ci-gate`, ветка должна быть актуальной;
   - нужно одобрение, в том числе **владельца критических файлов**
     (Require review from Code Owners);
   - одобрение сбрасывается после новых коммитов;
   - запрещены force push и удаление ветки;
   - правила действуют и для администраторов.
2. **CODEOWNERS.** Автор не может сам одобрить свой merge request, нужен
   второй участник команды.
3. **`make policy`** (этап 1) автоматически отклоняет:
   - удаление тестов — число тестовых функций не ниже `min_test_functions`
     и нижней границы в `check_policy.py`;
   - `skip`/`xfail` и `noqa`/`nosec` без обоснования;
   - снижение порогов покрытия и мутаций;
   - новые исключения ruff и bandit;
   - удаление шагов из `make verify`;
   - в pipeline: удаление этапа или его make-цели, `continue-on-error`,
     `|| true` после make, публикацию без зависимости от всех этапов;
   - критический файл без владельца в CODEOWNERS;
   - исключение уязвимости без обоснования или с истёкшим сроком.

   Понизить сами нижние границы можно только правкой `scripts/check_policy.py`.
   Это критический файл, такая правка требует одобрения владельца.
4. **Отчёт «Критические файлы»** в каждом merge request
   (`scripts/critical_changes.py`):
   - список изменённых критических файлов с их владельцами;
   - сравнение числа тестов «было/стало»;
   - аннотации прямо в диффе: удалённый тест — ошибка, изменённый
     критический файл — предупреждение.
5. **Dependabot** раз в неделю предлагает обновления pip, Docker и GitHub
   Actions. Каждое обновление проходит тот же CI.

## 9. Первоначальная настройка (один раз)

```bash
gh auth login
./scripts/setup_github.sh <логин-Александрова> <логин-Садыкова> <логин-Нургелдиева>
git add .github/CODEOWNERS && git commit -m "chore: владельцы критических файлов"
```

Скрипт:

- записывает логины в CODEOWNERS;
- создаёт секреты;
- даёт pipeline по умолчанию права только на чтение;
- создаёт окружение `registry`;
- включает защиту `main`.

То же через сайт:

- Settings → Branches → Add rule для `main`;
- Settings → Environments → `registry`;
- Settings → Secrets and variables → Actions.
