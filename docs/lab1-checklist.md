## Порядок демонстрации

1. **Приложение работает.**
   `make up && make migrate && make run`, затем сквозной сценарий из
   [`docs/api.md`](api.md): единица → поставщик → материал → поступление →
   проведение → отчёт по остаткам.
2. **Правило предметной области.** Провести документ дважды — показать ответ
   `422 business_rule_violated` и то, что остаток не задвоился.
3. **Обработка ошибок.** Запрос с ИНН «123» и запрос несуществующего материала.
4. **Проверки.** `make verify` — линтер, тесты и проверка, что `.env` не в git.
5. **Git-процесс.** `git log --oneline --graph --all`: задача → ветка →
   несколько коммитов → merge request → слияние → тег `v0.1.0`.
6. **Конфликт.** Показать коммит слияния и объяснить, какие правки объединялись.
7. **Секреты.** `git ls-files | grep -c "^\.env$"` → 0, при этом `.env` локально
   существует и приложение им пользуется.
8. **Контрольное изменение.** По просьбе преподавателя: создать issue, ветку,
   внести правку, `make verify`, merge request.

## Контрольное изменение: пример за 5 минут

```bash
git switch main && git pull
git switch -c feature/99-supplier-search       # 1. ветка от задачи
# 2. правка: добавить фильтр ?q= в список поставщиков (app/services.py, app/routers/suppliers.py)
# 3. тест на новое поведение в tests/test_catalogs.py
make verify                                     # 4. локальные проверки
git add -A && git commit -m "feat: поиск поставщиков по названию"
git push -u origin feature/99-supplier-search   # 5. merge request и ревью
```

## Смоделированный конфликт слияния

Конфликт возник в `CHANGELOG.md`: две ветки, созданные от одного коммита,
переписывали один и тот же пункт раздела «Добавлено».

| Ветка | Задача | Что меняла |
|---|---|---|
| `feature/3-reports` | #3 | добавила отчёты и правило проведения поступления |
| `docs/4-release-notes` | #4 | добавила пункты о тестах, линтере и окружении |

Первая ветка влилась в `main` без конфликта (MR !2), при слиянии второй git
сообщил `CONFLICT (content): Merge conflict in CHANGELOG.md`. Конфликт разрешён
вручную: сохранены обе правки, пункт про HTTP API объединён в один, порядок
пунктов приведён к «функциональность → инфраструктура»; после разрешения
повторно выполнена `make verify`.

Как показать это на защите:

```bash
git log --oneline --graph --all        # видны обе ветки и два коммита слияния
git log --merges --oneline             # список слияний
git show <хеш коммита слияния>          # разрешение конфликта
git show <хеш коммита слияния> -m -- CHANGELOG.md   # что пришло из каждой ветки
```

## Что нужно сделать на стороне GitHub/GitLab вручную

История веток, коммитов, разрешённый конфликт и тег уже в репозитории. На
сервере остаётся оформить то, что живёт не в git-истории:

```bash
git remote add origin <url вашего репозитория>
git push -u origin main
git push origin v0.1.0
```

1. Создать issue #2 «Поступления материалов», #3 «Отчёты по складу»,
   #4 «Заметки к релизу 0.1.0» (шаблон — `.github/ISSUE_TEMPLATE/task.md`).
2. Включить защиту ветки `main`: запрет прямого push, обязательный merge request
   и одобрение ревьюера.
3. Для контрольного изменения на защите создать новую задачу и провести её
   через ветку и merge request (пример — в разделе выше).

> Если преподаватель требует, чтобы merge request существовали на сервере как
> объекты, а не только в истории git, повторите ветки `feature/2-receipts`,
> `feature/3-reports` и `docs/4-release-notes` через веб-интерфейс: запушьте их
> отдельно и создайте MR до слияния.
