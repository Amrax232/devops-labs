# Складской учёт (warehouse-inventory)

Учебный проект по курсу **«Методология и практики DevOps»**.
Вариант проекта **№1 — складской учёт**: материалы, единицы измерения, поставщики,
поступления на склад и отчёты по ним.

Лабораторная работа №1: минимально работоспособное приложение с HTTP API и
реляционной базой данных, оформленный Git-процесс и зафиксированный регламент
внесения изменений.

## Назначение системы

Система ведёт учёт материалов на складе: хранит справочники материалов, единиц
измерения и поставщиков, регистрирует документы поступления и поддерживает
актуальные остатки. Подробное техническое задание — [`docs/tz.md`](docs/tz.md).

**Пользователи:** кладовщик (регистрирует поступления), снабженец (ведёт
поставщиков и номенклатуру), руководитель склада (смотрит отчёты).

## Быстрый старт

```bash
git clone <url-репозитория> && cd warehouse-inventory

make setup           # venv, зависимости, .env из .env.example
make up              # поднять PostgreSQL в контейнере
make migrate         # применить миграции
make run             # приложение на http://localhost:8000
```

Проверка: <http://localhost:8000/healthz>, интерактивная документация —
<http://localhost:8000/docs>.

Без Docker: поднимите свой PostgreSQL и укажите строку подключения в `.env`
(`DATABASE_URL`).

## Команды проверки

Единый интерфейс команд — всё запускается через `make`:

| Команда | Назначение |
|---|---|
| `make setup` | первоначальная настройка проекта |
| `make run` | локальный запуск приложения |
| `make test` | автоматические тесты |
| `make quality` | форматирование и статический анализ |
| `make migrate` | применение миграций базы данных |
| `make backup` | резервная копия базы (`backups/*.dump`) |
| `make restore FILE=...` | восстановление из резервной копии |
| `make verify` | **полный набор локальных проверок** |
| `make up` / `make down` | запуск/остановка контейнерного окружения |
| `make container-check` | проверка контейнерного окружения |

`make verify` обязателен перед созданием merge request: он проверяет, что `.env`
не отслеживается git, прогоняет линтер и все тесты.

## API

Полное описание с примерами запросов — [`docs/api.md`](docs/api.md),
интерактивная версия — `/docs` (OpenAPI).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/healthz`, `/readyz` | проверка работоспособности и готовности |
| GET/POST/DELETE | `/api/v1/units` | единицы измерения |
| GET/POST/PATCH/DELETE | `/api/v1/suppliers` | поставщики |
| GET/POST/PATCH/DELETE | `/api/v1/materials` | материалы и остатки |
| GET/POST/DELETE | `/api/v1/receipts` | поступления и их строки |
| POST | `/api/v1/receipts/{id}/post` | провести поступление |
| GET | `/api/v1/reports/stock` | отчёт по остаткам |
| GET | `/api/v1/reports/receipts` | отчёт по поступлениям |

Ошибки возвращаются в едином формате:

```json
{"error": {"code": "business_rule_violated", "message": "Проведённое поступление изменить нельзя", "details": {"receipt_id": 1}}}
```

## Правила предметной области

1. Поступление создаётся черновиком (`draft`) и в этом статусе редактируется.
2. **Проведение** (`POST /receipts/{id}/post`) увеличивает остатки материалов на
   количество из строк документа и переводит его в статус `posted`.
3. Проведённый документ нельзя изменить, дополнить или удалить, а также провести
   повторно — остатки не могут «задвоиться».
4. Нельзя провести документ без строк; количество в строке строго больше нуля.
5. Один материал встречается в документе не более одного раза.
6. Справочный объект нельзя удалить, пока на него ссылаются другие записи
   (поставщика с поступлениями можно только деактивировать).
7. Уникальны: код единицы измерения, артикул материала, ИНН поставщика (10 или
   12 цифр), номер поступления.

Каждое правило закрыто автоматическим тестом (`tests/test_receipts.py`).

## Регламент внесения изменений

Кратко (полная версия — [`docs/workflow.md`](docs/workflow.md)):

- любое изменение начинается с **задачи (issue)** и отдельной **ветки** вида
  `feature/<номер задачи>-<краткое-имя>`;
- прямые коммиты в `main` запрещены, изменения попадают в `main` только через
  **merge request** с ревью второго участника;
- перед merge request автор обязан выполнить `make verify` локально;
- **запрещено**: удалять или отключать тесты, ослаблять правила линтера ради
  прохождения проверки, коммитить `.env` и другие секреты, менять историю `main`;
- релиз помечается тегом (`v0.1.0` — результат лабораторной работы №1).

## Состав команды

| Участник | Зона ответственности |
|---|---|
| Участник 1 | материалы и единицы измерения (`units`, `materials`) |
| Участник 2 | поставщики (`suppliers`) |
| Участник 3 | поступления и отчёты (`receipts`, `reports`) |

Общие файлы (`Makefile`, `docker-compose.yml`, миграции, конфигурация) считаются
критическими: изменения в них отдельно отмечаются в merge request и проверяются
всей командой.
