# Складской учёт (warehouse-inventory)

Учебный проект по курсу **«Методология и практики DevOps»**.
Вариант проекта **№1 — складской учёт**: материалы, единицы измерения, поставщики,
поступления на склад и отчёты по ним.

Лабораторная работа №1: минимально работоспособное приложение с HTTP API и
реляционной базой данных, оформленный Git-процесс и зафиксированный регламент
внесения изменений.

## Назначение системы

Система ведёт учёт материалов на складе: хранит справочники материалов, единиц
измерения и поставщиков, регистрирует документы поступления и поддерживает
актуальные остатки. Подробное техническое задание — [`docs/tz.md`](docs/tz.md).

**Пользователи:** кладовщик (регистрирует поступления), снабженец (ведёт
поставщиков и номенклатуру), руководитель склада (смотрит отчёты).

## Быстрый старт

```bash
git clone <url-репозитория> && cd warehouse-inventory

make setup           # venv, зависимости, .env из .env.example
make lock            # один раз: зафиксировать версии (requirements.lock) и закоммитить
make up              # собрать образ и поднять всё: db → migrate → app1, app2 → nginx
make container-seed  # демонстрационные данные (по желанию)
```

Сервис доступен только через Nginx: <http://127.0.0.1:8080/docs>,
<http://127.0.0.1:8080/healthz>. Полная проверка контейнерной среды —
`make container-check`, описание — [`docs/containers.md`](docs/containers.md).

Разработка без пересборки образа — приложение из `.venv`, база в контейнере:

```bash
make dev-db          # только PostgreSQL, порт на 127.0.0.1:5432
make migrate         # миграции из .venv
make run             # приложение на http://localhost:8000 с автоперезагрузкой
```

Единый интерфейс команд — всё запускается через `make` (полный список — `make help`):

| `make coverage` | все тесты + отчёты JUnit и покрытия в `reports/` |
| `make mutation` | мутационное тестирование правил `app/domain.py` |
| `make lint` | формат и статический анализ (ruff) |

| `make backup` / `make restore FILE=...` | резервная копия и восстановление |
| `make restore-demo` | копия → повреждение → восстановление → сверка |
| `make verify` | **весь обязательный набор проверок** |
| `make ci` | весь pipeline CI локально, в том же порядке |
| `make secrets-scan` / `make deps-audit` / `make image-scan` | секреты в истории git, уязвимости зависимостей, анализ образа |
| `make migrations-check` / `make backup-check` | этапы CI «Миграции» и «Резервное копирование» |
| `make smoke [URL=...] [REVISION=...]` | проверка работающего релиза: служебные адреса, версия, основной сценарий |

| `make container-check` | полная проверка контейнерной среды (обязательна при её изменении) |
| `make container-lint` | статические запреты: `latest`, root, секреты, healthcheck, порты |

`make verify` обязателен перед каждым merge request. Он выполняет по порядку:
политику качества, проверку секретов (файлы и история git), линтер, SAST,
проверку зависимостей, запреты для контейнеров, конфигурацию мониторинга,
подготовку тестовой базы,
все уровни тестов с порогом покрытия 80 % и мутационное тестирование с порогом
80 %. Состав и назначение шагов — [`docs/quality-policy.md`](docs/quality-policy.md),
стратегия тестирования — [`docs/testing.md`](docs/testing.md).

## Непрерывная интеграция

GitHub Actions ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) запускается
при каждом `push` и merge request в `main`. Этапы:

1. стиль и политика;
2. тесты;
3. миграции;
4. резервное копирование;
5. безопасность (gitleaks, bandit, pip-audit);
6. контейнерная проверка и анализ образа (trivy);
7. публикация образа в `ghcr.io` с тегом по commit SHA — только из `main` и
   только после успеха всех этапов.

Каждый этап вызывает те же make-цели, что и `make verify` / `make ci` локально.

После успешного CI на `main` задание **CD (staging)** разворачивает образ в
тестовом окружении (ВМ `warehouse-stage`, self-hosted runner) и проверяет
выпуск: контейнеры, `/version`, основной сценарий. При неудаче выпуск не
принимается и возвращается предыдущая версия. Подробности — [`docs/cd.md`](docs/cd.md).
Слить изменение в `main` можно только при зелёной проверке `ci-gate` и с
одобрением владельца критических файлов (`.github/CODEOWNERS`). Подробности —
[`docs/ci.md`](docs/ci.md).

## Инфраструктура как код

Машины окружений `staging` и `production` настраиваются **только Ansible**
(`infra/`):

- пользователи, SSH, пакеты, Docker, каталоги и права, firewall (nftables);
- настройки и запуск приложения;
- runner.

Параметры разделены на общие, параметры окружения, параметры узла и
секреты (`ansible-vault`). Повторный запуск ничего не меняет, а ручные правки
отменяет. После применения доступность приложения проверяется автоматически.

```bash
make infra-setup                      # Ansible в infra/.venv
make infra-check ENV=staging          # что изменится (--check --diff)
make infra-apply ENV=staging          # привести к требуемому состоянию и проверить
make infra-idempotence ENV=staging    # повторный запуск: changed=0
```

Подробности — [`docs/infra.md`](docs/infra.md).

## Наблюдаемость

- **Журналы** — одна строка JSON на событие в `docker logs`: время, уровень,
  тип события, адрес операции, результат, `request_id` (общий для Nginx и
  приложения); секреты маскируются.
- **Метрики** — запросы, ошибки, время ответа, состояние, предметные
  (материалы ниже минимума, складские операции); хост (node-exporter),
  контейнеры (cAdvisor), доступность через Nginx (blackbox) → Prometheus.
- **Панель** Grafana — `http://127.0.0.1:8080/grafana/` (вход `admin` /
  `GRAFANA_ADMIN_PASSWORD`).
- **Оповещения** — 12 правил с unit-тестами и ссылкой на раздел
  [инструкции по диагностике](docs/runbook.md).

```bash
make status                         # всё о состоянии системы на одном экране
make logs-find LEVEL=ERROR SINCE=30m
make logs-find ID=<X-Request-ID из ответа>
make alerts
```

Подробности — [`docs/observability.md`](docs/observability.md), что делать
при сбое — [`docs/runbook.md`](docs/runbook.md).

## API

Полное описание с примерами запросов — [`docs/api.md`](docs/api.md),
интерактивная версия — `/docs` (OpenAPI).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/healthz`, `/readyz` | проверка работоспособности и готовности |
| GET/POST/DELETE | `/api/v1/units` | единицы измерения |
| GET/POST/PATCH/DELETE | `/api/v1/suppliers` | поставщики |
| GET/POST/PATCH/DELETE | `/api/v1/materials` | материалы и остатки |
| GET/POST | `/api/v1/materials/{id}/write-offs` | списания материала |
| GET/POST/DELETE | `/api/v1/receipts` | поступления и их строки |
| POST | `/api/v1/receipts/{id}/post` | провести поступление |
| GET | `/api/v1/reports/stock` | отчёт по остаткам |
| GET | `/api/v1/reports/receipts` | отчёт по поступлениям |

Ошибки возвращаются в едином формате:

```json
{"error": {"code": "business_rule_violated", "message": "Проведённое поступление изменить нельзя", "details": {"receipt_id": 1}}}
```

## Доступ к API

Права разграничены по типу операции:

| Кто | Чтение (GET) | Добавление, изменение, удаление (POST, PATCH, DELETE) |
|---|---|---|
| Пользователь без входа | разрешено | **запрещено** — ответ `401 unauthorized` |
| Пользователь, вошедший по логину и паролю | разрешено | разрешено |

Служебные адреса `/`, `/healthz`, `/readyz` открыты всегда. Если логин и пароль
переданы, они проверяются при любом запросе: с неверным паролем не получится
даже читать.

Логин и пароль задаются переменными окружения и в репозиторий не попадают:

```bash
AUTH_USERNAME=admin
AUTH_PASSWORD=warehouse123
```

Как войти:

- **Swagger** (`/docs`) — кнопка **Authorize** справа сверху;
- **curl** — флаг `-u`:

```bash
curl localhost:8000/api/v1/materials                         # читать можно без входа
curl -X POST localhost:8000/api/v1/units \
  -H 'Content-Type: application/json' -d '{"code":"kg","name":"Кг"}'   # 401
curl -u admin:warehouse123 -X POST localhost:8000/api/v1/units \
  -H 'Content-Type: application/json' -d '{"code":"kg","name":"Кг"}'   # 201
```

## Правила предметной области

1. Поступление создаётся черновиком (`draft`) и в этом статусе редактируется.
2. **Проведение** (`POST /receipts/{id}/post`) увеличивает остатки материалов на
   количество из строк документа и переводит его в статус `posted`.
3. Проведённый документ нельзя изменить, дополнить или удалить, а также провести
   повторно — остатки не могут «задвоиться».
4. Нельзя провести документ без строк; количество в строке строго больше нуля.
5. Один материал встречается в документе не более одного раза.
6. Справочный объект нельзя удалить, пока на него ссылаются другие записи
   (поставщика с поступлениями можно только деактивировать).
7. Уникальны: код единицы измерения, артикул материала, ИНН поставщика (10 или
   12 цифр), номер поступления.
8. **Списать можно не больше, чем есть на остатке.** Одновременные списания не
   «перерасходуют» остаток: строка материала блокируется на время операции.
9. Количество хранится с точностью до 3 знаков, цена — до 2; более точное
   значение отклоняется, а не округляется молча.

Решения «можно / нельзя» собраны в `app/domain.py` и проверяются unit-тестами
и мутационным тестированием; сценарии целиком — тестами API и интеграционными.
Соответствие пунктов ТЗ тестам — [`docs/test-matrix.md`](docs/test-matrix.md).

[`deploy/security.md`](deploy/security.md).

## Регламент внесения изменений

Кратко (полная версия — [`docs/workflow.md`](docs/workflow.md)):

- любое изменение начинается с **задачи (issue)** и отдельной **ветки** вида
  `feature/<номер задачи>-<краткое-имя>`;
- прямые коммиты в `main` запрещены, изменения попадают в `main` только через
  **merge request** с ревью второго участника;
- перед merge request автор обязан выполнить `make verify` локально;
- **запрещено**: удалять или отключать тесты, ослаблять правила линтера ради
  прохождения проверки, коммитить `.env` и другие секреты, менять историю `main`;
- релиз помечается тегом (`v0.1.0` — результат лабораторной работы №1).

| Участник | Зона ответственности |
|---|---|
| Участник 1 | материалы и единицы измерения (`units`, `materials`) |
| Участник 2 | поставщики (`suppliers`) |
