# История изменений

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версии — семантические.

## [0.8.0] — 2026-10-20

Результат лабораторной работы №6: непрерывная поставка в тестовое окружение
с проверкой работающего выпуска.

### Добавлено

- `GET /version` — версия и коммит работающего образа (`APP_REVISION`).
- Тестовое окружение `warehouse-stage` (ВМ Debian 12):
  - Docker;
  - отдельная учётная запись `deploy`;
  - self-hosted runner;
  - firewall;
  - настройки окружения в `stage.env` на сервере.
- `docker-compose.deploy.yml` — образ из реестра без сборки на сервере.
- `deploy/stage/deploy.sh`:
  - блокировка;
  - проверка настроек;
  - образ из реестра, файлы выпуска из коммита образа;
  - копия БД;
  - переключение;
  - проверка выпуска;
  - автоматический и ручной возврат;
  - история выпусков.
- `scripts/smoke_test.sh` и `make smoke` — проверка релиза: служебные адреса,
  версия, доступ, сквозной сценарий поступления и списания. Тот же сценарий
  выполняется в CI.
- `.github/workflows/deploy.yml` — автоматически после успешного CI на `main`;
  вручную — тег, возврат, состояние, имитация сбоев (healthcheck, сценарий,
  реестр, переменная).
- `scripts/setup_staging.sh` — окружение `staging`, `STAGING_URL`, одобрение
  запусков из форков, токен runner.
- `make policy` проверяет задания на self-hosted runner, а
  `make container-lint` — `docker-compose.deploy.yml`.
- `docs/cd.md`, `docs/lab6-checklist.md`.

### Изменено

- `/readyz` без базы данных отвечает 503. Healthcheck экземпляров проверяет
  готовность, а не только живость процесса.

## [0.7.0] — 2026-10-19

Результат лабораторной работы №5: непрерывная интеграция на GitHub Actions.

### Добавлено

- Pipeline `.github/workflows/ci.yml`: запуск при `push`, merge request в
  `main` и изменении `main`. Этапы:
  1. стиль и политика;
  2. тесты;
  3. миграции;
  4. резервное копирование;
  5. безопасность;
  6. контейнерная проверка и анализ образа;
  7. публикация.

  Единая обязательная проверка — `ci-gate`.
- Публикация образа в `ghcr.io` с тегами по commit SHA. Публикуется только из
  `main`, только после успеха всех этапов и только тот образ, что прошёл
  проверки.
- `make secrets-scan` (gitleaks по всей истории), `make deps-audit` (pip-audit
  по `requirements.lock`), `make image-scan` (trivy). Две первые цели входят в
  `make verify`.
- `make migrations-check`: миграции с нуля, `alembic check`, линейность, откат
  и повторное применение.
- `make backup-check`, `make ci` (весь pipeline локально), `make publish`,
  `make critical-changes`.
- `security/vulnerability-exceptions.toml` — исключения для уязвимостей с
  обоснованием и сроком пересмотра (общие для pip-audit и trivy).
- `.github/CODEOWNERS`, `scripts/setup_github.sh` (секреты, окружение
  `registry`, защита `main`), Dependabot.
- Отчёт «Критические файлы» в merge request: изменённые критические файлы и
  число тестов «было/стало».
- `scripts/ci_demo.sh` — сценарии с намеренными дефектами для демонстрации.
- `make policy` дополнительно проверяет:
  - минимум тестовых функций;
  - состав pipeline: нет `continue-on-error` и `|| true`, публикация зависит
    от всех этапов;
  - владельцев критических файлов;
  - исключения уязвимостей.
- Метки образа `org.opencontainers.image.revision` и `.source`.
- `docs/ci.md`, `docs/lab5-checklist.md`.

## [0.6.0] — 2026-10-19

Результат лабораторной работы №4: контейнеризация, балансировка и проверка
контейнерной среды.

### Добавлено

- `Dockerfile`: двухэтапная сборка, закреплённый базовый образ и
  `requirements.lock`, запуск от пользователя uid 10001, `HEALTHCHECK`, штатная
  остановка по `SIGTERM`. `.dockerignore` — белый список.
- `docker-compose.yml`: `db` → `migrate` → `app1`, `app2` → `nginx`.
  - Внутренние сети, наружу открыт только Nginx.
  - Именованный том БД.
  - Ограничения CPU, памяти и числа процессов.
  - Корневая ФС только на чтение.
- `docker-compose.dev.yml` — порт БД на 127.0.0.1 для разработки из `.venv`.
- Nginx — балансировщик:
  - round-robin;
  - исключение отказавшего экземпляра и повтор запроса на другом;
  - ограничение частоты (429);
  - заголовок `X-Upstream`.
- Заголовок `X-Instance-Id` в каждом ответе, поле `instance` в `/healthz`
  (настройка `INSTANCE_ID`).
- При остановке приложения закрывается пул соединений с БД.
- `make container-check` — полная проверка контейнерной среды в 14 шагов.
- `make container-lint` — статические запреты (`latest`, root, секреты,
  отключённый healthcheck, лишние порты), входит в `make verify`.
- `make restore-new-volume` — восстановление копии в новый пустой том со сверкой.
- Цели `build`, `ps`, `logs`, `dev-db`, `container-migrate`, `container-seed`.
- `docs/containers.md`, `docs/lab4-checklist.md`.

### Изменено

- `make up` поднимает всё окружение (раньше — только PostgreSQL). Для
  разработки из `.venv` используется `make dev-db`.
- Порт PostgreSQL больше не публикуется в основном окружении.
- Healthcheck БД проверяет готовность по TCP: при первом запуске на пустом
  томе база не считается готовой во время работы initdb.
- `make migrations-demo` выполняет alembic в контейнере `migrate`.
- Шаблон merge request: обязательный пункт `make container-check` для
  изменений контейнерной среды (контролирует `make policy`).

## [0.5.0] — 2026-10-17

### Изменено

- Разграничение прав доступа: просматривать данные (`GET`) может любой
  пользователь без входа, а добавлять, изменять и удалять (`POST`, `PATCH`,
  `DELETE`) — только после входа по логину и паролю. Неверные логин и пароль
  отклоняются при любом запросе, в том числе при чтении.

### Добавлено

- Тест, который находит в приложении все маршруты изменения данных и
  проверяет, что каждый закрыт: новый маршрут нельзя случайно оставить открытым.

## [0.4.0] — 2026-10-15

Результат лабораторной работы №3: автоматические проверки, миграции и
резервное копирование.

### Добавлено

- Списание материалов: `POST/GET /api/v1/materials/{id}/write-offs`, таблица
  `write_offs`; списать больше остатка нельзя, строка материала блокируется на
  время операции.
- Телефон поставщика и место хранения материала.
- Миграции `0002` (телефон), `0003` (место хранения, NOT NULL со значением по
  умолчанию), `0004` (списания).
- Модуль `app/domain.py`: правила предметной области в виде чистых функций.
- Три уровня тестов: unit, API на изолированной SQLite-базе, интеграционные на
  PostgreSQL (миграции на чистой и заполненной базе, лестница миграций, сверка
  моделей со схемой, ограничения СУБД, одновременные списания).
- Граничные тесты для всех параметров API.
- Мутационное тестирование `scripts/mutation_test.py`, порог 80 %.
- SAST (bandit), отчёты JUnit, покрытия (XML и HTML), порог покрытия 80 %.
- Политика качества `scripts/check_policy.py`: запрет пропуска тестов,
  исключений анализаторов без обоснования и снижения порогов.
- Проверка секретов `scripts/check_secrets.sh`.
- Резервное копирование с проверкой архива, контрольной суммой и ротацией;
  восстановление со страховочной копией в одной транзакции; демонстрации
  `make restore-demo` и `make migrations-demo`.
- `make lock` — снимок точных версий всех зависимостей.
- Документация: стратегия тестирования, матрица ТЗ → тесты, политика качества,
  миграции, резервное копирование, чек-лист ЛР3.

### Изменено

- `make verify` — единый контур из семи шагов (policy, secrets, lint, sast,
  test-db, coverage, mutation).
- `make lint` только проверяет формат (`ruff format --check`), исправляет —
  `make format`.
- Количество и цена отклоняются, если точнее, чем хранит база (3 и 2 знака).
- По умолчанию приложение слушает `127.0.0.1`; у пароля API больше нет
  значения по умолчанию — без `AUTH_PASSWORD` приложение не запускается.
- Миграции проверяются ruff наравне с остальным кодом.

## [0.3.0] — 2026-09-23

Результат лабораторной работы №2: развёртывание в Linux-среде.

### Добавлено

- Каталог `deploy/`: скрипты повторяемой установки на двух машинах Debian 12 —
  базовая настройка, ограничения SSH, PostgreSQL с пользователем минимальных
  прав, среда выполнения приложения, правила `ufw`.
- systemd-сервис `warehouse.service`: автозапуск при загрузке, перезапуск при
  аварийном завершении, ограничение привилегий процесса.
- Конфигурация вынесена в `/etc/warehouse/warehouse.env` (`EnvironmentFile`),
  в репозитории — только шаблон без секретов.
- `deploy/security.md` — зафиксированные правила безопасности, `deploy/checklist-lab2.md`
  — сценарии проверки на защите, `deploy/app/status.sh` — диагностика одной командой.

## [0.2.0] — 2026-09-23

### Добавлено

- Аутентификация HTTP Basic для всех маршрутов `/api/v1/**`: логин и пароль
  задаются переменными `AUTH_USERNAME` и `AUTH_PASSWORD`.
- Код ошибки `unauthorized` (401) в общем формате ответов, заголовок
  `WWW-Authenticate` для окна ввода в браузере.
- Скрипт `make seed` — наполнение базы демонстрационными данными.

### Изменено

- Открытыми без пароля остались только `/`, `/healthz` и `/readyz`.

## [0.1.0] — 2026-09-10

Результат лабораторной работы №1.

### Добавлено

- HTTP API на FastAPI: единицы измерения, поставщики, материалы, поступления, отчёты.
- Реляционная схема из пяти связанных таблиц и миграция Alembic `0001_initial_schema`.
- Правило предметной области: проведение поступления изменяет остатки;
  проведённый документ неизменяем.
- Единый формат ошибок и обработка некорректных запросов (404/409/422).
- Конфигурация через переменные окружения, `.env.example`, health-check `/healthz` и `/readyz`.
- Автоматические тесты (pytest) и статический анализ (ruff).
- Единые команды проверки в `Makefile`, контейнерный PostgreSQL, скрипты backup/restore.
- Документация: ТЗ, описание API, схема БД, регламент внесения изменений.
